# 目标、范围与验收标准

> 状态（2026-08-01）：本文涉及资源冲突、冲突中心、投入比例、冲突通知或冲突扫描的设计已由“删除资源冲突与投入比例”决策取代，仅保留历史背景，不代表当前实现。

## 1. 重构目标

本次重构不是给占位页换皮，而是从已清理的旧“Project + ProjectStage + 可变 Task + DDL 申请”模型转向“Task + Tag + 不可变计划版本 + Node + 人员时间结构”。

### 1.1 业务目标

- 让负责人能够看到 Task 当前有效计划、历史计划和每次修改原因。
- 通过 Milestone Review 区分“已投入工作”和“目标已验收”。
- 通过 Work Segment 看清人员现在做什么、未来安排、计划/实际差异和资源冲突。
- 保持重大操作可追溯，避免直接覆盖历史事实。
- 降低成员记录负担，优先批量、复用、拖拽、默认值和一次确认。

### 1.2 技术目标

- 把状态迁移、权限和不变量集中到领域服务，避免分散在页面和 action。
- 使用 PostgreSQL 约束、事务和乐观锁保证单当前版本、单 Active Milestone 和重复审批安全。
- 保留现有通知 outbox、结构化日志、附件鉴权和 Playwright 隔离数据库。
- 采用新增 migration 和分阶段启用，保护采购、反馈与共享基础设施数据。
- 为未来子 Task、并行节点和条件分支保留标识与关联能力，但本期不实现这些功能。

## 2. 本期范围

### 2.1 核心业务

- Task 独立存在、状态、成员、Tag、当前计划指针和归档。
- Plan Version 创建、历史、比较和只读。
- Milestone、Revision、Termination 三类 Node。
- Milestone Review 多次记录、撤销和最终有效结果。
- Planned / Actual Work Segment。
- Planned 与 Actual 的多对多来源关系、拆分、合并、部分确认。
- Allocation、Priority、业务 Role 和 Completion。
- Resource Conflict 检测、展示、确认和人工解决。

### 2.2 横切能力

- Person / Account 分离，飞书身份兼容。
- 系统、组织、Task 和对象所有者权限；Tag 不提供权限继承。
- 审计事件、逻辑删除、附件引用。
- 飞书与站内通知架构及偏好。
- cron 扫描、outbox、幂等和失败重试。
- 桌面、移动端和无障碍交互。
- schema 发布、维护窗口、监控、备份和回滚。

### 2.3 替代与删除范围

- 旧立项审批、ProjectStage、旧 Task、DDL、周报和旧风险流程及其运行时、数据和通知事件已经清理。
- 新流程不进行旧表双写，不提供旧 UI、旧接口或旧数据导入兼容。
- 新 Task 和 Tag 从空项目管理数据集创建，不增加旧 Project/Task 来源标记。
- 采购模块继续使用共享 User/角色/通知/附件设施，不改变采购业务状态机。

## 3. 非目标

- Task 内子 Task。
- Plan Version 内并行 Node、条件分支或循环。
- 自动依据 Work Segment 完成 Milestone。
- 自动依据到期时间完成 Milestone 或终止 Task。
- 自动移动人员计划来“解决”资源冲突。
- 用 Allocation、Completion 或实际投入自动评价个人绩效。
- 将外部飞书文档内容自动判定为验收通过。
- 在本轮同时重写采购模块。
- 将所有 `team` / `techGroup` 字符串立即规范化为完整组织主数据系统；本期只增加稳定的范围引用和兼容映射。
- 邮箱注册、密码登录、密码重置、设备管理和邮件通知。

## 4. 不可妥协的设计原则

1. 当前 Plan Version 唯一。
2. 每个 Plan Version 内 Node 顺序唯一且线性。
3. 未结束 Task 最多一个 Active Milestone。
4. 已生效计划和完成事实不可原地改写。
5. 计划语义修改必须通过 Revision。
6. 只有 Approved Review 能完成 Milestone 并推进 Task。
7. Work Segment 与 Task/Node 只引用，不互相自动改状态。
8. 重要对象逻辑删除，历史数据保留。
9. 自动化只做检测、提醒和建议，不替人做业务决定。
10. 所有写操作必须在服务端验证输入、权限、当前状态和并发版本。

## 5. 上线验收标准

### 5.1 功能验收

- 新建 Task 必须生成初始 Plan Version、至少一个 Milestone 和一个 Termination。
- 对 Active Milestone 修改目标、条件、时间或顺序时，UI 只能进入 Revision 流程。
- Revision 生效后，旧版本完整可见，新版本成为唯一 Current。
- 两个并发 Revision 只有一个可基于同一版本生效，另一个得到可理解的冲突提示。
- Review Approved 后只能推进到当前计划的下一个有效节点。
- Rejected 不推进；Revision Required 引导创建 Revision。
- 历史 Review 不被新 Review 覆盖；撤销只标记撤销记录。
- Planned Segment 可批量创建、拖拽、拆分、合并、取消和确认。
- Planned Segment 可生成一个或多个 Actual Segment；来源关系可追溯。
- 资源超配被标记并解释，但未经确认不修改任何 Segment。
- 用户只能查看和操作权限范围内的数据。

### 5.2 数据验收

- 每个新建 Task 恰好有一个 Current Plan Version。
- 每个非 Draft、非结束 Task 最多一个 Active Milestone。
- 新 schema 不包含旧 Project、Stage、旧 Task 或其从表，也不包含 `legacySource*` 或旧数据映射表。
- 无孤儿 Node、Plan Version、Review、Work Segment 来源或附件引用。
- 所有新表具有必要外键、唯一约束、检查约束和查询索引。

### 5.3 质量验收

- `npm run check` 通过。
- migration diff 通过，包含采购与反馈数据的快照副本上至少完成两次 schema 演练。
- `npm run build` 通过。
- 项目管理新领域测试、集成测试和 Playwright 测试通过。
- 采购、通知、附件和登录现有回归通过。
- 桌面 `1440x1000` 与 Pixel 5 无横向溢出、无 Next.js error overlay、无未处理浏览器错误。
- 权限敏感操作都有允许与拒绝测试。
- 通知测试全程 `NOTIFICATION_DELIVERY_DISABLED=true`。
- 性能基线在约定数据规模下达标；具体门槛见测试计划。

### 5.4 运维验收

- 有数据库备份、恢复验证、schema 发布报告和回滚演练记录。
- 关键指标可观测：action 错误率、Revision 冲突率、outbox 积压、cron 延迟、资源冲突扫描耗时、页面 p95。
- 维护模式、发布停止点和整库恢复流程已演练。
- 发布采用明确维护窗口；失败时恢复发布前数据库备份和上一镜像，不依赖旧项目管理 UI。
- 上线后值守人、升级路径和故障处理手册已确认。

## 6. 完成定义

单个工作包只有满足以下条件才可关闭：

- 业务规则、异常路径和验收标准明确。
- 服务端权限和状态校验完成。
- 数据写入在正确事务中，重复调用和并发行为明确。
- 审计、通知和日志已处理，或书面说明为什么不需要。
- 自动化测试覆盖主路径、拒绝路径和并发/失败路径。
- 桌面、移动、空状态、长文本、只读和终态界面已检查。
- 正式文档已从“计划”更新为“实际实现”。
- 独立审查没有未解决的高严重度问题。
