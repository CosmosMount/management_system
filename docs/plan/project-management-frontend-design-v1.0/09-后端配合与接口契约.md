# 09. 后端配合与接口契约

## 1. 总结

后端的领域对象与 Segment 操作能力已经较完整，足以支撑大部分拖拽甘特交互；真正缺口主要在：

1. **Task 草稿的增量编辑**。
2. **计划的明确开始时间与日期顺序校验**。
3. **面向画布的批量聚合查询**。
4. **人员、Task、Tag 的搜索选择接口**。
5. **细粒度 permission flags 与隐私安全 Busy 数据**。
6. **Task 元数据、成员、Tag 的修改动作**。
7. **即时冲突预览/复扫与乐观并发契约**。
8. **完整 Review、Audit 与统一首页待办查询**。

不建议为了前端重写现有 lifecycle/segment service；应在查询层和 Server Action 边界补齐契约。

## 3. P0 必需后端改动

## BE-01：Task 计划开始时间

### 问题

现有 Task 只有 `startedAt`，更接近实际激活/开始状态；`TaskPlanVersion` 没有计划开始。甘特图若只有第一个 Milestone 截止点，就无法准确表示第一阶段的起点和总计划范围。

### 建议

在 `TaskPlanVersion` 增加：

```prisma
plannedStartAt DateTime? @db.Timestamptz(6)
```

理由：计划开始属于版本化计划，而不是不可变 Task 元数据；Revision 可修改未来计划开始/基线。

### 迁移

- 旧数据可为空。
- 读取时 fallback：Task.startedAt → 最早相关 Segment → 第一个 Milestone 前的显示默认，但 UI 明确“未设置”。
- 新建 Task 建议要求 plannedStartAt；若业务允许为空，画布提示补充。

## BE-02：计划日期顺序服务端校验

### 问题

结构验证不足以保证拖动后的时间合理。

### 建议规则

- 每个 Milestone 的 `expectedCompletedAt >= plannedStartAt`。
- 按 sequence 的日期是否必须严格递增，由产品冻结；建议至少非递减。
- `termination.plannedAt >= 最后一个 Milestone.expectedCompletedAt`。
- 时间字段必须使用同一业务时区规则解析。
- Revision target plan 同样校验。

返回字段级错误：

```ts
{
  code: "PLAN_CHRONOLOGY_INVALID",
  issues: [
    { entityId: "node-id", field: "expectedCompletedAt", message: "不得早于上一 Milestone" }
  ]
}
```

## BE-03：Draft Task 增量更新

### 问题

`createTaskDraft` 只支持完整一次性创建；Task 创建后若仍为 Draft，现有前端没有 metadata、member、plan 的更新 Action。

### 建议 Actions

```ts
updateTaskDraftMetadata(input: {
  taskId: string;
  lockVersion: number;
  title: string;
  description: string;
  team: string;
  techGroup: string;
  priority: TaskPriority;
  revisionApprovalMode: RevisionApprovalMode;
  allowSelfReview: boolean;
  relatedTaskId: string | null;
  tagIds: string[];
}): ActionResult<TaskDraftSummary>

replaceTaskDraftPlan(input: {
  taskId: string;
  planVersionId: string;
  lockVersion: number;
  plannedStartAt: string | null;
  milestones: DraftMilestoneInput[];
  termination: DraftTerminationInput;
  idempotencyKey: string;
}): ActionResult<TaskPlanVersionDto>

replaceTaskDraftMembers(input: {
  taskId: string;
  lockVersion: number;
  members: Array<{ personId: string; role: TaskMemberRole }>;
}): ActionResult<TaskMemberDto[]>
```

### 规则

- 仅 Task.status = DRAFT。
- 仅 Current Plan.status = DRAFT。
- 事务更新。
- 使用 `lockVersion` 防止覆盖。
- 节点替换应保留可保留的 ID，或返回旧临时 ID 到新 ID 映射，防止 Segment 关联丢失。
- 若采用全量 replace，必须明确定义已存在 Segment 的处理。

### 更稳妥方案

对 Draft Plan 提供节点级 CRUD + reorder，但接口数量更多。P0 可采用 replace + ID 映射，前提是 Draft 期间不允许随意删除已有被 Segment 关联的节点，或进行关系迁移确认。

## BE-04：创建字段补齐

现有 `createTaskDraft` 输入建议补充：

- `allowSelfReview`。
- `relatedTaskId`。
- `plannedStartAt`。
- 可选 `initialSegments`（若 P1 支持创建时安排人员）。

所有 ID 需验证可见性和关联合法性。

## BE-05：画布聚合查询

### 问题

现有 `listWorkSegments` 偏单一过滤，单次最多约 100 项，不能高效支持“某些人员 + 某些 Task + 时间范围 + 冲突 + Busy”。

### 建议 Query

```ts
getTimeCanvasData(input: {
  rangeStart: string;
  rangeEnd: string;
  personIds?: string[];
  taskIds?: string[];
  tagIds?: string[];
  nodeIds?: string[];
  types?: WorkSegmentType[];
  statuses?: WorkSegmentStatus[];
  groupBy: "PERSON" | "TASK";
  includeTaskAnchors?: boolean;
  includeActual?: boolean;
  includeBusyBlocks?: boolean;
  includeConflicts?: boolean;
  personCursor?: string;
  personLimit?: number;
}): Promise<TimeCanvasDataDto>
```

### DTO

```ts
type TimeCanvasDataDto = {
  timezone: string;
  range: { startAt: string; endAt: string };
  rows: Array<{
    id: string;
    kind: "PERSON" | "TASK" | "GROUP";
    label: string;
    sublabel?: string;
    capacitySummary?: CapacitySummary;
    permission: { canCreateSegment: boolean };
  }>;
  anchors: TimeAnchorDto[];
  segments: TimeSegmentDto[];
  conflicts: TimeConflictDto[];
  nextPersonCursor: string | null;
  dataVersion: string;
};
```

### 查询规则

- 只返回与 `[rangeStart, rangeEnd)` 相交的 Segment。
- 对无详情权限的其他占用返回 Busy DTO，不返回 title/task/node。
- anchors 只返回用户可见 Task 的必要字段。
- conflict explanation 可在详情查询时再取，列表只给摘要。
- 限制最大时间跨度、personIds、taskIds 数量，防止大查询。

## BE-06：人员、Task、Tag 搜索

### 人员

现有 `listTimelinePeople` 只覆盖当前 actor 和已有 Segment 人员，不足以新增成员或为尚无 Segment 的人排期。

```ts
searchPeople(input: {
  query?: string;
  team?: string;
  techGroup?: string;
  activeOnly?: boolean;
  cursor?: string;
  limit?: number;
}): PersonOptionPage
```

返回 displayName、team、techGroup、账号可用状态、可选头像，不返回不必要敏感字段。

### Task

```ts
searchTaskOptions(input: {
  query?: string;
  statuses?: TaskStatus[];
  tagIds?: string[];
  mine?: boolean;
  cursor?: string;
  limit?: number;
}): TaskOptionPage
```

返回 id、title、status、priority、activeMilestone 摘要、permission。

### Tag

```ts
listTagOptions(input: { query?: string; includeArchived?: boolean }): TagOption[]
```

## BE-07：Segment permission flags 和并发令牌

### 问题

前端不能仅凭对象状态猜测能否移动/确认/取消。

每个 Segment DTO 建议返回：

```ts
permissions: {
  canViewDetails: boolean;
  canEdit: boolean;
  canMove: boolean;
  canResize: boolean;
  canSplit: boolean;
  canMerge: boolean;
  canCancel: boolean;
  canConfirm: boolean;
  canRelink: boolean;
  canSoftDelete: boolean;
};
versionToken: string; // updatedAt 或单独版本
```

mutation 输入携带 `expectedVersionToken`；陈旧时返回：

```ts
{ code: "STALE_SEGMENT", current: TimeSegmentDto }
```

前端据此回滚并提示。

## BE-08：即时冲突预览/重扫

### 问题

当前 cron 扫描适合后台一致性，但拖动后用户需要即时反馈。

### 建议

```ts
previewSegmentPlacement(input: {
  segmentId?: string;
  personId: string;
  startAt: string;
  endAt: string;
  allocation?: number | null;
  taskId?: string | null;
  priority?: TaskPriority;
}): ConflictPreviewDto
```

以及 mutation 成功后：

- 同事务或同步触发受影响人员/范围的冲突复算；或
- 返回 `conflictScanPending`，页面局部触发 `scanConflictsForPerson` 并刷新。

前端预览只能提示，最终规则以 mutation/服务端复算为准。

## BE-09：隐私安全 Busy Block

Task 工作台需要看到参与人的其他占用，但不能泄露内容。

建议 DTO：

```ts
type BusyBlockDto = {
  id: string; // 可为稳定但不可反推原记录的 opaque id
  personId: string;
  startAt: string;
  endAt: string;
  allocation: number | null;
  type: "BUSY";
  visibility: "BUSY_ONLY";
  conflictSummary?: { severity: string };
};
```

不返回 Task 名、内容、Tag、Node、创建人。若用户有详情权限，返回普通 Segment DTO。

## 4. P1 后端改动

## BE-10：Task 元数据、成员与 Tag 修改

即使 Active Task 计划必须走 Revision，元数据和成员仍需独立更新契约：

- `updateTaskMetadata`。
- `addTaskMember` / `updateTaskMemberRole` / `removeTaskMember`，或 replace with lock。
- `replaceTaskTags`。
- `setRelatedTask`。

每项需：权限、审计、通知影响、锁版本、状态限制。

## BE-11：完整 Review 查询

当前工作台若只带最近结果，不足以渲染验收页。需要：

- Milestone 的全部 Review 历史。
- Evidence 摘要和按需详情。
- 当前用户可执行动作。
- revoked 状态。
- 分页。

## BE-12：Task 审计查询

```ts
listTaskAuditEvents(input: {
  taskId: string;
  eventTypes?: string[];
  actorId?: string;
  cursor?: string;
  limit?: number;
}): AuditEventPage
```

DTO 提供业务摘要、发生时间、操作者、可展开 before/after；敏感字段脱敏。

## BE-13：统一 Action Inbox / Dashboard Overview

```ts
getMyWorkDashboard(input: {
  from: string;
  to: string;
  actionLimit: number;
  taskLimit: number;
}): {
  metrics: ...;
  personalTimeline: ...;
  actionInbox: ActionInboxItem[];
  activeTasks: ActiveTaskDashboardItem[];
  recentNotifications: ...;
};
```

服务端统一排序和权限过滤，避免客户端拼多个列表。

## BE-14：保存资源视图

P1 若实现保存视图，需要模型：owner、name、query config、isDefault、createdAt/updatedAt。配置必须版本化或包含 schemaVersion。

## BE-15：Segment 重新指派（可选）

若产品确实需要跨人员拖动：

```ts
reassignPlannedSegment(input: {
  segmentId: string;
  fromPersonId: string;
  toPersonId: string;
  expectedVersionToken: string;
  reason: string;
}): ActionResult<TimeSegmentDto>
```

必须处理：

- 谁能给谁重新指派。
- 原人员/新人员通知。
- 冲突复算。
- 审计记录。
- Task 成员关系是否要求。

没有此接口前，前端明确禁止跨行投放。

## 5. Task 创建 + 初始 Segment 的事务策略

有三种方案：

### 方案 A：P0 不在创建时建 Segment

- 创建 Task 后跳工作台再安排。
- 后端无需改事务。
- 最稳妥，推荐 P0。

### 方案 B：复合事务 Action

```ts
createTaskDraftWithSegments({ task, plan, members, segments })
```

- 全部成功或失败。
- 需要临时 node key 到真实 nodeId 映射。
- 适合正式支持后采用。

### 方案 C：前端串联

先 `createTaskDraft`，再 `batchCreatePlannedSegments`。

- 第二步失败时 Task 已创建。
- 需要补偿 UI 和重试队列。
- 不建议把它伪装成原子成功。

## 6. 建议错误契约

统一 ActionResult：

```ts
type ProjectManagementError = {
  code:
    | "VALIDATION_ERROR"
    | "FORBIDDEN"
    | "NOT_FOUND"
    | "INVALID_STATE"
    | "STALE_TASK"
    | "STALE_SEGMENT"
    | "CONFLICT_DETECTED"
    | "PLAN_CHRONOLOGY_INVALID"
    | "ASSOCIATION_INVALID"
    | "UNKNOWN";
  message: string;
  fieldIssues?: Array<{
    path: string;
    entityId?: string;
    message: string;
  }>;
  currentVersion?: unknown;
  retryable?: boolean;
};
```

前端不依赖英文 message 判断类型，只依赖稳定 code。

## 7. 日期范围与分页约束

建议服务端默认限制：

- 画布最大自定义范围，例如 366 天；超过需分段或导出。
- personIds/taskIds 每次请求上限。
- 每页人员数，例如 50。
- Segment 数量超过阈值时返回聚合/提示，不直接截断而不告知。
- `[start, end)` 半开区间契约统一，避免边界重复。

具体阈值由真实数据压测决定，不能在前端硬编码为业务事实。

## 8. 权限矩阵建议

后端应按“对象 + 动作”返回最终判断，而不是只返回几个 Task 级权限：

| 对象 | 动作 |
|---|---|
| Task | view, updateMetadata, manageMembers, manageTags, activate, archive |
| Plan | editDraft, createRevision, submitRevision, reviewRevision |
| Milestone | submitReview, review, viewEvidence |
| Termination | confirm |
| Segment | viewDetails, createForPerson, edit, move, resize, split, merge, cancel, confirm, relink, deleteActual |
| Conflict | view, acknowledge, resolve, ignore, applySuggestion |

权限返回只是 UI 辅助，Server Action 内仍重复授权。

## 9. API 完成优先级

| 优先级 | 能力 | 阻塞页面 |
|---|---|---|
| P0-Blocker | plannedStartAt + chronology validation | Task 创建、完整计划带 |
| P0-Blocker | TimeCanvas 聚合查询 | Task 详情、资源甘特、个人时间线 |
| P0-Blocker | person/task/tag 搜索 | 创建页、筛选、成员编辑 |
| P0-Blocker | permission flags + versionToken | 安全拖动与编辑 |
| P0 | Draft Task 更新 | 创建后继续编辑、Draft 工作台 |
| P0 | Busy DTO | Task 详情参与人其他安排 |
| P0 | 即时 conflict preview/re-scan | 拖动体验 |
| P1 | metadata/member/tag mutations | Task 概览完整编辑 |
| P1 | full reviews/audit | 验收和审计标签 |
| P1 | dashboard action inbox | `/progress` 完整重构 |
| P1/P2 | saved views / reassign | 高级资源管理 |
