### 8.3 发布桌演顺序与停止点

1. T-24h：冻结 release commit 和 migration checksum；确认最近一次空库、共享快照、恢复、性能、全量 E2E 和安全结果；收齐 BO/TL/QA/DBA 签字。缺任一项即停止。
2. T-30m：启用维护模式，停止 Web 写入、cron 和 outbox worker；记录队列深度、共享表 row/hash、项目管理关键表计数和上传 manifest。任何后台仍写入即停止。
3. T0：完成整库和上传 volume 备份，恢复到隔离环境并核对 manifest。备份不可读、恢复失败或 hash 不同即停止。
4. T+15m：仅由 DBA 在维护窗口执行已审查 migration；记录每条 migration、耗时和锁等待。出现失败、超时、非预期 DDL 或共享表变化即保持维护模式并进入回滚决策。
5. T+30m：运行 identity backfill dry-run；存在冲突即停止。APPLY 后再次执行，必须 `created=0` 且无冲突。
6. T+45m：部署固定 build，执行登录、采购/反馈冒烟、Task 创建/查询、Resource Planner、通知 outbox 禁直发和完整性巡检。任一 P0/P1 异常即不开放写入。
7. T+60m：BO/TL/QA/DBA 共同确认是否开放写入；恢复 cron/outbox 前再次检查机器人用途、delivery guard、allowlist 和积压量。开放写入是独立签字点。

### 8.4 回滚规则

- 开放写入前失败：保持维护模式，停止应用和 worker，按已演练流程恢复发布前数据库及上传 volume，核对共享表/全库/上传 manifest，再部署上一固定 build。
- 开放写入后失败：先停止写入和外部投递，记录受影响时间窗与新增业务写入。默认整库恢复会丢失窗口内新写入；必须由 BO/TL/DBA 明确选择“接受丢失并恢复”或“停止回滚并另立经审查的数据导出/重放方案”。不得临场编写未审查 SQL。
- 任何回滚都记录触发指标、决策人、快照标识、开始/结束时间、数据损失评估、恢复验证和通知外发状态；恢复后仍执行采购、反馈与项目管理联合冒烟。
