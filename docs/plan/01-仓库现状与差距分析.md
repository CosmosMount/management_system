## 3. 核心数据模型差距

| v2.1 要求 | 当前实现 | 差距 | 处理 |
|---|---|---|---|
| 所有执行对象统一为 Task | `Project`、`ProjectStage`、`Task` 三层且 `Task.projectId` 必填 | 对象层级与目标冲突 | 删除 Project/Stage 运行模型；旧 Project 与旧 Task 均迁成新 Task，分类改用 Tag |
| Task 具有 Plan Version | 无对应模型 | 无法保留完整历史计划 | 新增 `TaskPlanVersion` 与当前版本指针 |
| Plan Version 是 Node 单链 | 只有 ProjectStage 和 Task 自身 | 对象层级不同 | 新增 Task 内 `TaskNode` 与 `PlanVersionNode` |
| Node 三类 | 无 Milestone/Revision/Termination 模型 | 核心缺失 | 新增三类细节表或一对一模型 |
| Revision 不覆盖旧计划 | `TaskDdlChangeRequest` 只改 `Task.dueAt`；`updateTask` 原地改字段 | 只能记录申请，无法还原计划版本 | 新建 Revision 草稿和原子生效事务 |
| Milestone 多次 Review | `ApprovalRecord` 对 submission 唯一 | 一次提交只能一条审批，语义在 Task 层 | 新增 `MilestoneReview`，支持多次、撤销和最新有效结果 |
| 唯一当前版本和 Active Milestone | 无 | 无数据库保证 | 部分唯一索引 + 指针 + 事务断言 |
| Work Segment | 无 | 人员计划与实际完全缺失 | 新增 Segment、来源关系、历史和批量操作 |
| Person 与 Account 分离 | `User` 同时表示登录人和业务人员，`openId` 必填 | 无未注册 Person | 新增 Person、Account、AccountIdentity；本期只启用飞书身份 |
| Resource Conflict | 只有 Task/Stage 风险 | 无时间重叠与 Allocation 分析 | 新增可解释扫描器和冲突记录 |
| 通知渠道 | 进度主要飞书；无站内收件箱 | 站内历史与偏好不足 | 首发扩展站内通知并保留飞书 outbox；邮件不纳入本期 |
| 逻辑删除 | Task 有 `deletedAt`，Project 多为状态；若干关系 Cascade | 历史链可能被级联删除 | 重要业务表改 Restrict/SetNull，统一 deletion metadata |

## 4. 业务规则差距

### 4.1 计划与执行

当前 Task 主流程是：

```text
TODO -> IN_PROGRESS -> PENDING_ACCEPTANCE -> COMPLETED -> ARCHIVED
```

Task 提交一次 DELIVERY，审批后 Task 直接完成。该流程与 v2.1 的差异是：

- 没有多个 Milestone。
- 没有当前 Node。
- 没有 Termination 确认。
- 无法通过 Revision 替换当前或未来计划。
- `updateTask` 可以原地修改 title、goal、负责人、指标等；需要区分“元数据”与“计划语义”。
- `TaskDdlChangeRequest` 只处理 dueAt，无法同时修改目标、条件、顺序和后续节点。
- 当前 `ProjectStage` 顺序验收整体删除，不迁成 Milestone。

### 4.2 验收

当前已有“交付提交 -> 审批通过/驳回”闭环，且有验收清单快照。这是可复用资产，但需要变化：

- 验收对象从 TaskSubmission/Task 迁移到 Milestone。
- Review Result 增加 `REVISION_REQUIRED` 与 `PENDING` 语义。
- 同一 Milestone 允许多次 Review；每次都保留。
- 撤销 Review 不删除记录。
- Approved 必须在同一事务中完成 Milestone、激活下一节点或进入 Termination 确认。

### 4.3 人力资源

现有 `TaskAssignee`、`ProjectParticipant` 和 `ProjectStageOwner` 只说明关系，不说明时间段、计划/实际、Allocation 或工作内容。WeeklyReport 是周维度文字汇报，不能等价为 Actual Segment。因此人力模块必须新建，不应从周报推算。

### 4.4 权限

`canViewProject()` 和 `canViewTask()` 当前只要已登录就返回 true，列表查询也对已登录用户开放全部进度数据。v2.1 要求“只能查看有权限的数据”，因此这是 P0 行为变更：

- 新模型按“Task 成员与系统管理角色可见”实现，不从 Tag 继承权限。
- 页面查询和所有 action 必须复用同一授权策略。
- UI 隐藏不能代替服务端授权。
- 独立 Task 没有 Project 范围，需要自己的组织范围与成员关系。

### 4.5 账号

当前 `User.openId` 唯一且必填，`email` 可空但未声明唯一。首发已确认只支持飞书身份，但仍需把登录身份与业务 Person 分离：

- 采购和飞书回调仍大量使用 `User.openId`，共享身份改造必须先保证采购行为不变。
- 项目管理新表直接引用 `Person` / `Account`；旧项目管理 openId 字段随旧功能一起删除。
- 本期不新增密码字段、邮箱登录、密码重置、设备管理或邮件通知。
- 模型可预留 provider 类型，但本期只启用 `FEISHU`。

## 5. 界面差距

现有页面以 Project 详情、Task 详情、任务看板和统一审批为主。重构后 Project 页面整体删除，并新增：

- Task 当前计划时间线。
- Revision 分叉视觉与版本比较。
- 历史 Plan Version 只读视图。
- Milestone Review 时间线。
- Termination 确认。
- 人员维度时间轴、任务维度人员投入和计划/实际对比。
- Segment 批量创建、拖拽、拆分、合并、部分确认。
- Resource Conflict 双入口提示。
- 站内通知中心与按事件/渠道偏好。
- Account 登录渠道、设备和安全事件管理。

现有组件可复用，但不建议把所有新逻辑继续堆入 `task-detail-workspace.tsx`。应拆分领域查询和可独立测试的子面板。

## 6. 操作与接口差距

当前主要通过 Server Actions 写入，符合仓库惯例。问题在于：

- 领域规则散落在多个 action。
- Task 状态、提交、审批、DDL 修改和更新各自查询相似对象并重复判断。
- 审计 payload 多为字符串 JSON，缺少统一 schema/version。
- 部分业务状态提交后调用 `drainNotificationOutboxSoon()`，技术文档已标为后续治理项。
- 没有统一 idempotency key；多数路径依赖状态 `updateMany` 或唯一索引。
- 批量 Segment 操作需要明确单批大小、部分失败策略和幂等语义。

目标是保留 Server Action 入口，但让 action 只负责认证、输入解析和结果映射；事务与不变量进入 `lib/project-management/*`。

## 7. 测试差距

现有测试基础较好，覆盖进度审批、通知、阶段负责人、任务导入、安全和完整业务流。新增领域仍需补：

- 纯状态机/不变量表驱动测试。
- Revision 版本构造和差异算法测试。
- PostgreSQL 部分唯一索引、检查约束和并发事务测试。
- Review 重复提交、并发审批和撤销测试。
- Segment 拆分/合并/转换的守恒测试。
- Allocation 跨时区、跨日和边界重叠测试。
- 资源冲突解释和幂等扫描测试。
- Person/Account 绑定冲突与采购兼容回归。
- 历史数据迁移对账和回滚演练。
- 大量节点、版本和 Segment 下的性能测试。

## 8. 文档漂移

`docs/TECH.md` 的“进度管理”状态图仍描述旧的 `DRAFT/NORMAL/ABNORMAL/...` 流程，与当前 Prisma enum `ESTABLISHING/NOT_STARTED/IN_PROGRESS/...` 不一致；同一段还称 ProjectStage 为“里程碑”。重构前必须先建立“代码基线事实表”，实施后同步更新：

- `README.md`
- `docs/TECH.md`
- `docs/TESTING.md`
- `docs/NOTIFICATIONS.md`
- `docs/project_management/*`
- `.env.example`

不得让本计划替代正式的“已实现行为”文档。

## 9. 风险最高的改动面

1. `User.openId` 到 Account/Person 的映射会影响采购、权限、通知和飞书回调。
2. 删除 Project/Stage 会影响大量 `task.project.*`、列表、权限、通知和审批假设。
3. 旧 Project 与旧 Task 迁入同一新 Task 表时必须处理 ID、状态和成员映射。
4. Revision 生效同时写多表，存在并发和半完成风险。
5. 一次性切换和删除旧运行时能力要求更严格的迁移演练、维护窗口与整库恢复预案。
6. 通知事件数量明显增加，收件人过滤和 outbox 积压需压测。
7. 资源时间轴可能产生大范围查询和前端渲染性能问题。

开发期可以用仅限非生产环境的模块开关分段验收，但生产切换不保留旧 UI 或双写。所有破坏性清理必须先在生产数据副本上演练。
