# 仓库现状与差距分析

> 状态（2026-08-01）：本文涉及资源冲突、冲突中心、投入比例、冲突通知或冲突扫描的设计已由“删除资源冲突与投入比例”决策取代，仅保留历史背景，不代表当前实现。

## 1. 审计基线

- 审计日期：2026-07-28
- 数据库：PostgreSQL 16 + Prisma 7
- Web：Next.js App Router + Server Actions
- 身份：Auth.js + 飞书 OAuth
- 测试：Playwright，桌面与移动项目
- 项目管理：旧运行时、专用 schema 和开发数据已清理；`/progress` 已替换为新项目管理首批工作台入口

本章以清理后的仓库为基线。此前版本的旧 Project/Stage/Task 行为只作为删除背景，不是迁移源或当前能力。

## 3. 核心数据模型差距

| v2.1 要求 | 当前实现 | 差距 | 处理 |
|---|---|---|---|
| 所有执行对象统一为 Task | 当前无项目管理业务模型 | 核心模型尚未实现 | 新增 Task 与 Tag，不增加 Project 或旧来源字段 |
| Task 具有 Plan Version | 无对应模型 | 无法保留完整历史计划 | 新增 `TaskPlanVersion` 与当前版本指针 |
| Plan Version 是 Node 单链 | 当前无对应模型 | 核心缺失 | 新增 Task 内 `TaskNode` 与 `PlanVersionNode` |
| Node 三类 | 无 Milestone/Revision/Termination 模型 | 核心缺失 | 新增三类细节表或一对一模型 |
| Revision 不覆盖旧计划 | 当前无对应模型 | 核心缺失 | 新建 Revision 草稿和原子生效事务 |
| Milestone 多次 Review | 当前无对应模型 | 核心缺失 | 新增 `MilestoneReview`，支持多次、撤销和最新有效结果 |
| 唯一当前版本和 Active Milestone | 无 | 无数据库保证 | 部分唯一索引 + 指针 + 事务断言 |
| Work Segment | 当前无项目管理模型 | 人员计划与实际完全缺失 | 新增 Segment、来源关系、历史和批量操作 |
| Person 与 Account 分离 | `User` 同时表示登录人和业务人员，`openId` 必填 | 无未注册 Person | 新增 Person、Account、AccountIdentity；本期只启用飞书身份 |
| Resource Conflict | 当前无对应模型 | 无时间重叠与 Allocation 分析 | 新增可解释扫描器和冲突记录 |
| 通知渠道 | 共享 outbox、飞书传输层和采购/反馈 adapter 已保留；无项目管理 adapter 或站内收件箱 | 业务事件与站内历史尚未实现 | 新增项目管理 adapter 与站内通知；邮件不纳入本期 |
| 逻辑删除 | 当前无项目管理模型 | 需要从新 schema 建立历史保护 | 重要业务表使用 Restrict/SetNull 和 deletion metadata |

## 4. 业务规则差距

### 4.1 计划与执行

旧 Task 主流程已经随旧实现删除。清理后的仓库没有可沿用的 Task 状态机；v2.1 的 Milestone、当前 Node、Termination 与 Revision 必须按目标不变量从零实现。

### 4.2 验收

旧“交付提交 -> 审批通过/驳回”闭环和验收清单已删除，不作为兼容接口。新 Review 需要：

- 验收对象直接定义为 Milestone。
- Review Result 增加 `REVISION_REQUIRED` 与 `PENDING` 语义。
- 同一 Milestone 允许多次 Review；每次都保留。
- 撤销 Review 不删除记录。
- Approved 必须在同一事务中完成 Milestone、激活下一节点或进入 Termination 确认。

### 4.3 人力资源

当前没有项目管理成员、周报或人员投入数据。人力模块必须新建，不能假设存在可回填的 Actual Segment。

### 4.4 权限

旧项目管理权限 helper 已删除。v2.1 必须从第一个查询和 action 起实现“只能查看有权限的数据”：

- 新模型按“Task 成员与系统管理角色可见”实现，不从 Tag 继承权限。
- 页面查询和所有 action 必须复用同一授权策略。
- UI 隐藏不能代替服务端授权。
- Task 没有 Project 范围，需要自己的组织范围与成员关系。

### 4.5 账号

当前 `User.openId` 唯一且必填，`email` 可空但未声明唯一。首发已确认只支持飞书身份，但仍需把登录身份与业务 Person 分离：

- 采购和飞书回调仍大量使用 `User.openId`，共享身份改造必须先保证采购行为不变。
- 项目管理新表直接引用 `Person` / `Account`。
- 本期不新增密码字段、邮箱登录、密码重置、设备管理或邮件通知。
- 模型可预留 provider 类型，但本期只启用 `FEISHU`。

## 5. 界面差距

当前 `/progress`、Task 列表/工作台、资源时间轴、冲突中心和站内通知中心已上线。v2.1 后续仍需补齐：

- Task 当前计划时间线。
- Revision 分叉视觉与版本比较。
- 历史 Plan Version 只读视图。
- Milestone Review 时间线。
- Termination 确认。
- 人员维度时间轴、任务维度人员投入和计划/实际对比。
- Segment 批量创建、拖拽、拆分、合并、部分确认。
- Resource Conflict 双入口提示。
- 站内通知中心与按事件/渠道偏好。

只复用共享 UI 原语，不恢复已删除的旧项目管理组件。新工作台应拆分领域查询和可独立测试的子面板。

## 6. 操作与接口差距

当前主要通过 Server Actions 写入，符合仓库惯例。问题在于：

- 领域规则散落在多个 action。
- 新项目管理尚无 action 和领域 service。
- 审计 payload 多为字符串 JSON，缺少统一 schema/version。
- 部分业务状态提交后调用 `drainNotificationOutboxSoon()`，技术文档已标为后续治理项。
- 没有统一 idempotency key；多数路径依赖状态 `updateMany` 或唯一索引。
- 批量 Segment 操作需要明确单批大小、部分失败策略和幂等语义。

目标是保留 Server Action 入口，但让 action 只负责认证、输入解析和结果映射；事务与不变量进入 `lib/project-management/*`。

## 7. 测试差距

现有测试只覆盖项目管理占位和旧路由重定向。新增领域需要补：

- 纯状态机/不变量表驱动测试。
- Revision 版本构造和差异算法测试。
- PostgreSQL 部分唯一索引、检查约束和并发事务测试。
- Review 重复提交、并发审批和撤销测试。
- Segment 拆分/合并/转换的守恒测试。
- Allocation 跨时区、跨日和边界重叠测试。
- 资源冲突解释和幂等扫描测试。
- Person/Account 绑定冲突与采购兼容回归。
- 新 schema 部署、共享数据保护和回滚演练。
- 大量节点、版本和 Segment 下的性能测试。

## 8. 文档漂移

正式文档已改为描述占位状态和共享飞书基础设施。实施每个阶段后仍需同步更新：

- `README.md`
- `docs/TECH.md`
- `docs/TESTING.md`
- `docs/NOTIFICATIONS.md`
- `docs/project_management/README.md`
- `.env.example`

不得让本计划替代正式的“已实现行为”文档。

## 9. 风险最高的改动面

1. `User.openId` 到 Account/Person 的映射会影响采购、权限、通知和飞书回调。
2. 新项目管理必须从第一版就使用统一飞书传输层和独立 channel adapter，避免绕过 outbox。
3. Revision 生效同时写多表，存在并发和半完成风险。
4. 新 schema 上线仍要求维护窗口、共享数据保护和整库恢复预案。
5. 通知事件数量明显增加，收件人过滤和 outbox 积压需压测。
6. 资源时间轴可能产生大范围查询和前端渲染性能问题。

开发期可以用仅限非生产环境的模块开关分段验收，但生产切换不恢复旧 UI 或双写。所有 schema 变更必须先在含采购与反馈数据的副本上演练。
