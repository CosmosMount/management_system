# Schema 发布与回滚

> 状态（2026-08-01）：本文涉及资源冲突、冲突中心、投入比例、冲突通知或冲突扫描的设计已由“删除资源冲突与投入比例”决策取代，仅保留历史背景，不代表当前实现。

## 1. 已确认的数据原则

旧项目管理实现和开发数据已在 v2.1 建设前直接清理。新系统从空项目管理数据集开始，不执行以下操作：

- 旧 Project 转新 Task。
- 旧 Task 转新 Task。
- 旧 Project 名称生成 Tag。
- 旧 Stage、成员、提交、审批、周报、风险、评论、关注、提醒或附件回填。
- `legacySource*`、migration map、`migrationNeedsReview` 或 legacy Tag。

发布期间必须保护采购、反馈、`User`、`UserRole`、`FileAsset`、`NotificationOutbox`、`NotificationOutboxRecipient` 和采购 CardKit 跟踪数据。

## 2. Migration 结构

项目管理 v2.1 只使用新增 migration：

1. 创建 Account、AccountIdentity、Person 及必要约束。
2. 如设计需要，为已有 `User` 幂等建立 Account/Person 关联；保留 `User` 和采购外键不变。
3. 创建 Tag、Task、Plan Version、Node、Review、Segment、Conflict、站内通知和审计表。
4. 增加部分唯一索引、check、外键和查询索引。
5. 在代码和数据验证通过后启用新 `/progress` 入口与 worker。

migration 不 rename、读取或 drop 已清理的旧项目管理表。任何发现旧表或 `channel=progress` 历史记录的环境都视为基线漂移，停止发布并先审计环境，不能临时加入兼容回填。

## 3. 共享身份 backfill

若 Account/Person 上线需要为现有用户初始化关联，脚本必须：

- 以 `User.id/openId/unionId` 的稳定身份为输入，不按姓名合并。
- dry-run 输出总数、可创建数、已存在数、冲突数和脱敏冲突标识。
- APPLY 使用显式开关，并按唯一键幂等；重复运行不创建重复 Account、Identity 或 Person。
- `unionId` 冲突、一个 User 对应多 Account、一个 Person 绑定多 Account 时硬失败。
- 不修改采购使用的 `User.openId`、`unionId`、角色和关系。

该步骤属于共享身份初始化，不是旧项目管理对象迁移。

## 4. 发布前验证

在空数据库和含代表性共享数据的隔离 PostgreSQL 快照各执行至少两次：

1. `npm run db:deploy`。
2. Prisma validate/generate 和 migration diff。
3. 记录所有新增表、enum、索引和外键。
4. 对采购、反馈、用户、角色、附件、outbox/recipient、CardKit 跟踪表记录行数和稳定字段 hash。
5. 执行 Account/Person dry-run 和 APPLY（若适用），再重复执行验证幂等。
6. 运行项目管理 schema 约束与并发测试。
7. 运行采购、反馈、认证、附件和通知完整回归。
8. 验证 `/progress` 新入口和所有未匹配旧地址的路由行为。

硬门禁：

- 共享表行数或稳定字段 hash 意外变化。
- migration 试图访问不存在的旧 Project/Task 表。
- schema 出现 `legacySource*` 或旧项目管理 enum/关系。
- Account/Person 身份冲突不为零。
- 采购、反馈、认证或通知安全回归失败。
- 自动化测试产生真实飞书网络投递。

## 5. 发布顺序与停止点

### 5.1 准备

1. 冻结发布分支并记录镜像、migration 版本和配置 hash。
2. 停止 Web、cron 和飞书 worker，确认没有运行中的 outbox claim。
3. 备份 PostgreSQL 和上传 volume，并在隔离环境验证可恢复。
4. 记录共享表基线行数/hash、outbox 积压和 CardKit 跟踪数量。

### 5.2 Schema

1. 执行新增 migration。
2. 执行共享身份 backfill（若适用）。
3. 运行结构约束、孤儿关系和共享数据对账。

此时若失败，保持服务停止并恢复数据库，不启动新代码。

### 5.3 应用切换

1. 部署新应用镜像。
2. 先启动 Web，执行只读健康检查和 `/progress` 冒烟。
3. 验证采购、反馈、登录、附件和 outbox 入队。
4. 再启动 cron 与飞书 worker，观察 claim、失败率和积压。

切换后不提供旧项目管理 UI、旧 schema 或旧数据导入回退。

## 6. 回滚

### Stop A：migration 前

直接恢复上一镜像并启动服务，数据库不变。

### Stop B：migration/backfill 中或验证失败

保持所有进程停止，恢复发布前整库备份和上传 volume 快照，再部署上一镜像。禁止手工删除部分新表后继续发布。

### Stop C：新代码启动后、尚未产生新项目管理业务数据

停止进程并整库恢复，然后部署上一镜像。

### Stop D：已经产生新项目管理业务数据

默认仍整库恢复到发布前快照，并明确公告维护窗口内新写入会丢失。若业务要求保留这些写入，必须停止回滚并另立经审查的数据导出/重放方案；不得临场写 SQL。

## 7. 发布报告

报告至少记录：

- migration 名称、开始/结束时间和执行人。
- 备份标识与恢复验证耗时。
- 共享身份 backfill 计数和冲突数。
- 新 schema 约束检查结果。
- 共享表发布前后行数/hash 对账。
- 采购、反馈、认证、附件、outbox/CardKit 回归结果。
- outbox 积压、失败率和 worker 启动状态。
- 停止点、异常、决策人和最终结论。
