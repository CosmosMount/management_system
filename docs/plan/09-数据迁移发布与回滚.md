# 数据迁移、发布与回滚

## 1. 已确认的迁移原则

迁移只保留两类旧业务主对象：

- 每条旧 `Project` 转换为一条新 `Task`。
- 每条旧 `Task` 转换为一条新 `Task`。

旧 Project 名称同时生成 Tag：

- 由旧 Project 转换出的新 Task 关联该 Tag。
- 原来属于该 Project 的旧 Task，在转换后也关联该 Tag。

除构建新 Task 所需的顶层字段、负责人/参与人、组织范围和截止时间外，其余旧项目管理数据全部删除，不迁移：

- ProjectStage 及负责人。
- 立项申请/审批信息。
- Task/Stage submission、approval 和 checklist confirmation。
- Project/Task DDL change request。
- Task creation/deletion request。
- WeeklyReport。
- Task/Stage risk。
- Project comment。
- Follow preference。
- 旧 reminder rule、delivery 和 progress notification 事件。
- ProgressActivityLog 中的旧项目管理历史。

不做旧 UI、旧查询、双写或旧表兼容。

## 2. 一次性维护窗口

由于新旧 schema 不兼容，生产切换采用停机迁移：

1. 停止 Web、cron 和飞书 worker。
2. 备份 PostgreSQL 与上传文件。
3. 把旧 Project/Task 表改名为迁移源表。
4. 创建最终新 Task/Tag/Plan/Node/Person 等表。
5. 执行 Project -> Task、Task -> Task。
6. 对账新 Task 数量、状态、成员和 Tag。
7. 删除全部旧项目管理表和代码。
8. 部署新应用并冒烟。

失败时恢复整库备份和上一版本镜像，不尝试让旧应用连接新 schema。

## 3. 物理表切换

推荐在维护窗口中：

```text
Project       -> LegacyProject
Task          -> LegacyTask
ProjectOwner  -> LegacyProjectOwner
...
```

然后创建最终名称的：

- `Task`
- `Tag`
- `TaskTag`
- `TaskMember`
- `TaskPlanVersion`
- `TaskNode`
- `PlanVersionNode`
- `MilestoneNode`
- `RevisionNode`
- `TerminationNode`
- `Person` / `Account` / `AccountIdentity`
- Work Segment、Conflict、Notification、Audit 表

PostgreSQL rename 会保留旧外键指向 legacy 表，便于读取。迁移结束再按显式白名单 drop legacy 表，禁止通配符批量删除。

## 4. 迁移脚本

新增 `scripts/migrate-project-management-v2.ts`：

- 默认 dry-run。
- 必须设置 `APPLY_PM_V2_MIGRATION=true` 才写入。
- 强制 `NOTIFICATION_DELIVERY_DISABLED=true`。
- 校验目标数据库名、schema version 和维护模式。
- 用 `PmV2MigrationRun` 记录 runId、commit SHA、开始/结束、计数和结果。
- 用临时 `PmV2MigrationMap(sourceType, sourceId, targetTaskId)` 对账。
- 按批事务迁移，批大小默认 500。
- 可在 contract migration 前安全重跑；不得重复创建 Task/Tag。
- 输出 JSON 报告。

迁移不产生站内或飞书通知。

## 5. 身份与成员

项目管理新模型使用 Person：

1. 已有 User 按 openId/unionId 创建 Account、FEISHU Identity 和 Person。
2. 采购继续使用 User，不改采购外键。
3. 关系表中只有 openId、但 User 不存在时，创建无 Account 的 Person，名称取关系快照。
4. unionId 冲突时停止迁移，禁止按姓名自动合并。

成员映射：

| 来源 | 新 TaskMember |
|---|---|
| LegacyProject.ownerOpenId / ProjectOwner | OWNER |
| LegacyProjectParticipant | MEMBER |
| LegacyTask.assigneeOpenId / TaskAssignee | OWNER |

同一 Person 重复时去重，OWNER 优先。每条迁移 Task 至少一个 OWNER；缺失时迁移报告设为硬失败，维护窗口前人工修正。

ProjectStageOwner 不迁移。

## 6. 旧 Project -> 新 Task

### 6.1 基本字段

| 旧 Project | 新 Task |
|---|---|
| name | title |
| description | description |
| team/techGroup | Task 自身组织范围 |
| owners/participants | TaskMember |
| createdAt/updatedAt | 保留 |
| archivedAt | archivedAt |
| id | `legacySourceId`，新 Task 使用新 UUID |

`legacySourceType = PROJECT`，与 sourceId 组合唯一。

### 6.2 Tag

- 每个旧 Project 创建一个独立 Tag。
- Tag 名称默认等于 Project.name；出现同名时按确定规则追加短 ID，例如 `项目名 · a1b2c3`。
- 转换出的 Project Task 关联该 Tag。
- 该 Project 下所有旧 Task 转换后关联同一 Tag。

Tag 保存 `legacySourceId`，禁止把两个旧 Project 因同名而自动合并。

### 6.3 初始计划

每个旧 Project 只生成：

1. 一个 Milestone。
2. 一个 Termination。
3. 一个初始 Plan Version。

Milestone：

- goal = Project.name。
- description = Project.description。
- completionCriteria = `迁移任务：由 Task Owner 在首次 Revision 中补充完成条件`。
- expectedCompletedAt：
  1. 取该 Project 下 Stage 的最大非空 dueAt，仅作为汇总截止值；
  2. 否则取 completedAt/canceledAt；
  3. 仍为空则取 updatedAt。
- `migrationNeedsReview = true`。

Stage 的名称、顺序、goal、evidence、审批和风险不进入新数据。

### 6.4 状态

| 旧 ProjectStatus | 新 Task |
|---|---|
| ESTABLISHING | DRAFT，Version CURRENT，Milestone PENDING |
| NOT_STARTED | DRAFT，Version CURRENT，Milestone PENDING |
| IN_PROGRESS | ACTIVE，Milestone ACTIVE |
| COMPLETED | COMPLETED，Milestone COMPLETED，Termination SUCCESS |
| CANCELED | CANCELLED，Termination CANCELLED |
| ESTABLISHMENT_WITHDRAWN | CANCELLED，Termination CANCELLED |
| ESTABLISHMENT_REJECTED | CANCELLED，Termination CANCELLED |

迁移产生的 ACTIVE Project Task 首次打开时必须显示“计划由旧 Project 汇总生成，请通过 Revision 完善”。

## 7. 旧 Task -> 新 Task

### 7.1 基本字段

| 旧 Task | 新 Task |
|---|---|
| id | 尽量保留原 UUID；冲突时新 UUID + mapping |
| title | title |
| goal | description |
| team/techGroup/TaskTechGroup | Task 自身组织范围 |
| urgency + importance | priority |
| assignees | TaskMember OWNER |
| createdAt/updatedAt | 保留 |
| archivedAt/deletedAt | 保留 |

优先级：

- HIGH + HIGH -> CRITICAL。
- 任一 HIGH -> HIGH。
- LOW + LOW -> LOW。
- 其他 -> MEDIUM。

原 `projectId` 不保留为父子关系，只用于关联由旧 Project 名称生成的 Tag。

### 7.2 初始计划

每条旧 Task 只生成：

- Milestone goal = title。
- Milestone description = goal。
- completionCriteria = metrics；空值时写“迁移后待补充”并标记 `migrationNeedsReview=true`。
- expectedCompletedAt = dueAt。
- 一个 Termination，plannedAt = dueAt。
- 一个初始 Plan Version。

验收清单、submission、approval、DDL、weekly 和 risk 不迁移。

### 7.3 状态

| 旧 TaskStatus | 新状态 |
|---|---|
| TODO | DRAFT，Version CURRENT，Milestone PENDING |
| IN_PROGRESS | ACTIVE，Milestone ACTIVE |
| PENDING_ACCEPTANCE | ACTIVE，Milestone ACTIVE |
| COMPLETED | COMPLETED，Milestone COMPLETED，Termination SUCCESS |
| ARCHIVED | ARCHIVED，Milestone COMPLETED，Termination SUCCESS |
| PROJECT_CANCELED | CANCELLED，Termination CANCELLED |

PENDING_ACCEPTANCE 不保留旧待审批记录；迁移后回到 Active，需按新 Review 流程重新提交。

## 8. 删除清单

对账通过后 drop：

- LegacyProject、LegacyProjectOwner、LegacyProjectParticipant。
- LegacyProjectStage、LegacyProjectStageOwner。
- LegacyProjectDdlChangeRequest、LegacyProjectStageRiskRecord。
- LegacyTask 及旧 TaskAssignee、TaskTechGroup。
- TaskSubmission、ApprovalRecord、ApprovalChecklistConfirmation。
- TaskAcceptanceChecklistItem。
- TaskCreationRequest、TaskDeletionRequest、TaskDdlChangeRequest。
- WeeklyReport、TaskRiskRecord、ProjectComment。
- Project/Task FollowPreference。
- 旧 ProgressReminderRule、旧 ProgressApprovalReminderDelivery 中项目管理专用数据。
- 旧 ProgressActivityLog。
- 只服务旧项目管理的 enum、索引和 FK。

共享表处理：

- User/UserRole：保留，采购仍使用。
- NotificationOutbox：只删除或取消旧 progress channel 记录，采购/反馈不动。
- FileAsset：删除仅属于旧项目管理且不被其他域引用的记录和文件；先生成明确列表。
- AcceptanceChecklistTemplate：若只服务旧 Task，删除；若其他域使用则保留。

## 9. 对账硬门禁

必须满足：

```text
new Task count
= LegacyProject count
+ LegacyTask count
```

另检查：

- 每条 LegacyProject/LegacyTask 有且只有一个 migration map。
- 每条新 Task 至少一个 OWNER。
- 每条新 Task 恰好一个初始 Plan Version、一个 Milestone、一个 Termination。
- ACTIVE Task 恰好一个 Active Milestone。
- 结束 Task 的 Termination outcome 与状态一致。
- LegacyTask 有 projectId 时，新 Task 有对应 Tag。
- Project 转换 Task 也有对应 Tag。
- Tag 关联数符合每个旧 Project 的 `1 + old task count`。
- deleted/archived 状态计数一致。
- 采购表行数和 hash 不变。

旧 Stage/submission 等只核对“已按清单删除”，不核对迁移数量。

## 10. 演练

生产快照至少两次：

1. 演练一：发现缺 owner、同名 Tag、ID 冲突、状态异常和性能问题。
2. 演练二：全流程计时；不允许手工改 DB。

报告记录：

- Project/Task 源数量与新 Task 数。
- Tag 数与关联数。
- 每种状态映射数。
- 删除表清单。
- 迁移与 drop 耗时。
- 新 Task 抽样截图。
- 采购回归结果。
- 恢复备份耗时。

## 11. 发布 runbook

1. 冻结代码和数据写入。
2. 停止 Web、cron、飞书 worker。
3. `pg_dump` + 上传 volume 快照。
4. 验证备份可读取。
5. rename legacy 表并创建新 schema。
6. dry-run 迁移，核对数量。
7. APPLY 迁移。
8. 执行硬门禁。
9. drop 旧项目管理 schema。
10. 部署新应用。
11. 冒烟：飞书登录、Task 列表/详情、Revision、Review、Segment、站内通知。
12. 采购完整冒烟。
13. 启动 cron/worker。
14. 业务负责人签字并结束维护。

## 12. 回滚

- drop 前失败：停止并修脚本，legacy 表仍在。
- drop 后失败：停止全部进程，恢复数据库和上传 volume，部署旧镜像。
- 不允许部分恢复。
- 不允许旧应用连接新数据库。
- 发布前必须完成一次整库恢复演练。
