# 通知、定时任务与外部集成

> 状态（2026-08-01）：本文涉及资源冲突、冲突中心、投入比例、冲突通知或冲突扫描的设计已由“删除资源冲突与投入比例”决策取代，仅保留历史背景，不代表当前实现。

## 1. 首发渠道

本期只支持：

- `IN_APP`：站内通知，业务事务内创建。
- `FEISHU`：飞书私信，通过共享 outbox、项目管理 channel adapter 和统一传输层投递。

本期不支持邮箱登录和邮件通知。现有采购老师邮件保持原行为，不扩展到新项目管理事件。

## 2. 基本规则

1. 业务状态与站内通知/outbox 计划在同一事务内落库。
2. 飞书发送失败不回滚业务状态。
3. 每个业务事件有稳定 event key 和 payload version。
4. 收件人在入队时固化，后续角色变化不改变历史投递计划。
5. 站内通知是默认记录渠道；用户关闭飞书后仍可在站内看到。
6. 审批、安全和关键状态事件可设为强制，不能完全关闭。
7. Web 进程只入队，cron/worker 统一 drain。
8. 自动化测试必须禁用真实投递。

## 3. 事件矩阵

| 事件 | 站内 | 飞书 | 默认收件人 | 强制 |
|---|---:|---:|---|---:|
| Draft Task 成员初次加入（既有 `task_assigned`） | ✓ | ✓ | active TaskMember | 是（`mandatory=true`） |
| Active Task 成员新增/移除/角色变化 | ✓ | ✓ | 受影响成员及按现有策略确定的 Task 管理者 | 是（`mandatory=true`） |
| Task 激活 | ✓ | ✓ | Task 成员 | 否 |
| Milestone 即将到期 | ✓ | 偏好 | Owner/Lead/执行成员 | 否 |
| Milestone 逾期 | ✓ | ✓ | Owner/Lead/执行成员 | 是 |
| 提交 Milestone Review | ✓ | ✓ | 合法 Reviewer | 是 |
| Review Approved/Rejected | ✓ | ✓ | 提交人、Owner | 是 |
| Review 要求 Revision | ✓ | ✓ | 提交人、Owner/Lead | 是 |
| Revision 已创建 | ✓ | 偏好 | Owner/Lead | 否 |
| Revision 待审批 | ✓ | ✓ | 合法 Reviewer | 是 |
| Revision 通过/驳回 | ✓ | ✓ | 发起人、Owner | 是 |
| Revision 已生效 | ✓ | ✓ | Task 成员、受影响 Segment 人员 | 是 |
| Planned Segment 即将开始 | ✓ | 偏好 | Segment Person | 否 |
| Planned Segment 待确认 | ✓ | 偏好 | Segment Person | 否 |
| Planned Segment 关联失效 | ✓ | ✓ | Person、Resource Manager | 是 |
| Resource Conflict 新增 | ✓ | ✓ | Person、Resource Manager、Task Owner | 高严重度强制 |
| Conflict 已解决 | ✓ | 偏好 | 涉及人员 | 否 |
| Task Terminated | ✓ | ✓ | Task 成员 | 是 |
| Account/权限安全事件 | ✓ | ✓ | 受影响 Account、管理员 | 是 |

Tag 创建、改名、归档默认不广播；删除影响 Task 分类时只给操作者站内确认。

`createTaskDraft` 必须保留既有 `task_assigned` 事件及当前 `mandatory=true` 强制语义，不能因新增 Active 成员 action 而遗漏 Draft 事件。`replaceTaskMembers` 的每个新增、移除和角色变化也沿用成员变化强制规则：在业务事务中写完整站内通知和 `mandatory=true` 的 `project-management` outbox，复用现有 adapter；消息包含操作者、Task、动作、受影响人员、变更前后角色和结果。

`mandatory=true` 只表示成员变化通知不受普通偏好关闭影响，不改变机器人用途。Draft `task_assigned` 与 Active 成员变化的 purpose/botKind 均为 `notification`，只使用通知机器人，不是 approval bot。`replaceTaskTags` 只写 TaskTag 与审计，不广播；Draft tags 由 `updateTaskDraftMetadata` 更新。

## 4. 事件键

示例：

```text
pm:task:activated:<taskId>:<lockVersion>
pm:milestone:review_submitted:<reviewId>
pm:milestone:overdue:<nodeId>:<localDate>
pm:revision:applied:<revisionId>
pm:segment:confirmation_due:<segmentId>:<endAt>
pm:conflict:opened:<fingerprint>
pm:task:terminated:<terminationNodeId>
```

重复 cron、页面重试或 worker 重启不能产生重复投递。

## 5. 站内通知

`InAppNotification` 至少保存：

- recipientAccountId
- type/category
- title/summary
- entityType/entityId
- linkPath
- payloadVersion
- createdAt/readAt

业务对象权限在打开通知时重新检查。通知本身不保存敏感正文。对象已删除或权限撤销时仍可标记已读，但不展示对象详情。

## 6. 飞书消息

### 6.1 机器人路由

- Review 和 Revision 待处理：审批机器人。
- 到期、冲突、状态结果、指派：通知机器人。
- 项目管理 adapter 只能声明 `FeishuMessagePurpose`，不能自行选择凭据或调用飞书 API。
- 独立审批机器人缺少 unionId 时保持失败并重试；仅统一传输层可以在已定义的“用户对审批应用不可用”条件下记录并执行 notification fallback。

### 6.2 传输接口

- `lib/feishu-message.ts` 是唯一 IM 私信出口，接受 `FeishuMessage` 并返回 `FeishuSendResult`。
- 传输层负责 `open_id`/`union_id`、双机器人凭据、token、禁发开关、allowlist、CardKit 和错误脱敏，不查询 Task、成员或权限。
- 新项目管理 Server Action 和领域 service 只能入队，禁止直接导入 `sendFeishuDirectMessage()`。
- 群 Webhook 保持独立；新项目管理首发不定义 Webhook 通知。

### 6.3 卡片内容

至少包括：

- 操作者。
- Task 名称。
- Tag。
- 当前 Plan Version。
- Milestone/Revision/Conflict 摘要。
- 状态或变化。
- 时间。
- 可执行链接。

卡片按钮只作为入口；真实操作进入系统后重新认证和授权。除非后续单独设计并审查，不在本期支持飞书卡片直接审批。

## 7. 通知偏好

按类别配置：

- Task 更新。
- Milestone 时间提醒。
- Review。
- Revision。
- Work Segment。
- Resource Conflict。

每类可选择：

- 站内：保持开启；普通事件可静音未读角标，但记录仍存在。
- 飞书：开/关。

强制事件忽略用户关闭飞书：

- 待本人审批。
- 重大权限/账号变化。
- Revision 已生效且影响本人 Planned Segment。
- 高严重度资源冲突。
- Task 最终结束。

系统管理员配置团队默认值和强制列表，变更写审计。

## 8. 定时任务

| Worker | 建议频率 | 作用 | 是否改业务状态 |
|---|---|---|---:|
| `scanMilestoneDeadlines` | 每 10 分钟 | 临期/逾期提醒 | 否 |
| `scanSegmentTransitions` | 每 10 分钟 | 即将开始、待确认 | 只更新提示状态，不生成 Actual |
| `scanResourceConflicts` | 每 15 分钟增量 | 生成/更新冲突 | 不调整 Segment |
| `drainNotificationOutbox` | 每 2 分钟 | 飞书投递 | 否 |
| `cleanupNotificationRetention` | 每日 | 按策略清理已读站内通知 | 否 |
| `validateProjectManagementIntegrity` | 每日 | 检查 Current/Active/孤儿关系 | 否，只报警 |

项目管理业务时区冻结为 `Asia/Shanghai`。cron 业务日期、临期/逾期 event key、UAT 日期和发布报告中的业务日期都按该时区解释；数据仍存 UTC，事件键使用业务日期时必须带时区。

## 9. Outbox 改造

复用现有 `NotificationOutbox` 和 `NotificationOutboxRecipient`：

- 新 payload 类型统一在 `lib/project-management/notifications/events.ts`。
- 在 `lib/notification-channels/` 新增独立项目管理 adapter，按共享 `NotificationChannelAdapter` 契约校验 payload、去重收件人、构造消息并声明用途。
- 入队函数只接受已授权领域事件，不从 UI 文本拼 payload。
- recipient 级重试。
- 使用 `FOR UPDATE SKIP LOCKED` 优化并发 claim。
- 记录 `lockOwner`、`lockedUntil`、attempts、lastError。
- 达到最大重试次数进入 Failed，并在管理页显示。

## 10. 失败与降噪

- 同一 Milestone 的临期提醒每天最多一次，逾期按策略重复。
- 同一开放 Conflict 不重复通知，严重度上升时可再次通知。
- Revision 生效的多条 Segment 影响合并为一张摘要卡。
- 飞书失败不重复创建站内通知。
- 无合法收件人时仍保留审计，并向管理员运营面板报告配置缺失。
- 用户 Account 禁用后停止飞书投递，但不删除站内历史。

## 11. 清理后通知边界

旧立项、ProjectStage、Task DDL/创建/删除、WeeklyReport、旧 Risk、reminder 的事件、卡片、收件人计算和扫描器已删除。采购与反馈继续使用共享 outbox、各自 channel adapter 和统一飞书传输层；新项目管理事件只能按本章从零定义，不能复用旧 payload。

## 12. 测试要求

- 每个事件断言 eventKey、消息用途、收件人、中文标题、linkPath 和 payloadVersion。
- 关闭飞书偏好时，站内有记录且无飞书 recipient。
- 强制事件无视普通偏好。
- 重复入队只保留一条 outbox。
- recipient A 成功、B 失败后只重试 B。
- `NOTIFICATION_DELIVERY_DISABLED=true` 时不发真实消息。
- allowlist 仍生效。
- 静态检查确认项目管理 action/service 不导入飞书传输层，IM API 仍只由统一出口调用。
- 采购通知全回归，确保共享 outbox 改造无行为变化。
