# 测试策略与验收用例

## 1. 测试分层

| 层 | 目的 | 工具 |
|---|---|---|
| L0 静态 | Prisma、TS、ESLint、diff | 现有 npm scripts |
| L1 领域 | 状态机、不变量、diff、冲突算法 | Node test runner + tsx 或 Playwright test runner |
| L2 数据库集成 | 事务、约束、并发、schema 发布 | 隔离 PostgreSQL |
| L3 Action | 认证、授权、校验、审计、outbox | 集成测试 |
| L4 UI E2E | 用户主流程、响应式、可访问性 | Playwright |
| L5 非功能 | 性能、安全、恢复、数据对账 | 脚本 + 人工演练 |

若引入 Node 内置 test runner，增加 `test:domain`，不额外引入大型测试依赖。

## 2. 领域状态机测试

### 2.1 Task

- Draft 可激活、取消；不可直接 Completed。
- Active 只能经 Termination 进入结束状态。
- Completed/Failed/Cancelled/Timeout 只能归档。
- Archived 不恢复、不编辑。
- 到期扫描不改变 Task 状态。

### 2.2 Plan Version

- 每 Task 只能一个 Current。
- Version sequence 唯一、Node sequence 连续。
- 末尾必须 Termination。
- 不允许零 Milestone。
- Historical/Current 核心字段不可更新。
- Revision 不得修改 Completed 前缀。
- 基线过期拒绝生效。

### 2.3 Node

- 未结束 Task 最多一个 Active Milestone。
- Pending Milestone 不可 Review Approved。
- Approved 后正确推进下一 Milestone。
- 最后 Milestone Approved 后进入 Termination 确认。
- Rejected/Revision Required 不推进。
- Revision 生效后旧 Active -> Revised，新 Active 唯一。

## 3. Revision 测试

- 修改目标、条件、时间、顺序的 diff 正确。
- 新增/删除/移动 Node 可区分。
- Completed Node 在编辑器和服务端都锁定。
- Direct/Review Required 策略正确。
- 自审被拒绝。
- 并发两个 Revision 只有一个生效。
- 相同 idempotencyKey 不重复创建版本。
- 生效事务任一步失败时无半成品 Current。
- 受影响 Planned Segment 标记待确认，Actual 不变。

## 4. Review 测试

- 同 Milestone 多次 PENDING/Rejected/Revision Required 历史保留。
- 最新未撤销结果计算正确。
- checklist 未全勾选不能 Approved。
- evidence 必填规则。
- 重复点击不重复推进。
- 两个 Reviewer 并发只有一个处理当前 Pending。
- 撤销未推进 Review。
- 已推进 Approved 只能走受限纠错。
- 无权 Reviewer 被拒绝且无数据写入。

## 5. Termination 测试

- Success 要求前置 Milestone 全 Completed。
- Failed/Cancelled/Timeout 必填原因。
- 提前结束会取消未完成 Node。
- Task 与 Termination 状态一致。
- 重复确认幂等。
- 到期扫描不能自动确认 Timeout。

## 6. Work Segment 测试

### 6.1 校验

- endAt > startAt。
- Allocation `(0,100]`。
- Completion `[0,100]`。
- Node 必须属于关联 Task。
- 跨日、跨月、夏令时边界。

### 6.2 操作

- 创建、更新、拖拽、批量移动。
- 拆分后时间范围守恒且不重叠。
- 合并仅允许同人同语义。
- 一 Planned -> 多 Actual。
- 多 Planned -> 一 Actual。
- 部分确认覆盖范围正确。
- 一键一致确认。
- 取消不物理删除。
- Actual 逻辑删除保留 change history。
- Revised Node 只提示，不自动迁移。

建议增加性质测试思路：任意合法拆分/合并后总覆盖时长和来源关系保持。

## 7. Resource Conflict 测试

- Allocation 恰好 100% 不冲突，100.01% 冲突。
- 边界相接不视为重叠。
- 多段交叉计算正确。
- 缺 Allocation、High/Critical、Owner/Lead 规则。
- unavailable time 冲突。
- 同 fingerprint 重复扫描不重复。
- 冲突解除后状态更新。
- ignoredUntil 到期重新开放。
- preview suggestion 不写数据。
- apply suggestion 需要明确确认和版本校验。

## 8. 权限测试

每个敏感 action 至少一允许、一拒绝：

- Sys Admin、Team Admin 范围内/范围外。
- Task Owner、Lead、Member、Reviewer、Viewer。
- 非成员。
- 本人 Segment、他人 Segment。
- Tag 创建人但不是 TaskMember，确认无 Task 权限继承。
- 有 Tag 与无 Tag 的 Task 权限一致。
- 账号禁用。
- 自审。
- 被移除成员旧会话。
- 列表过滤和详情防枚举。
- 附件下载授权。

## 9. 通知测试

- 站内记录与业务事务一致。
- 飞书 eventKey、botKind、recipient 和卡片内容。
- 普通偏好关闭、强制事件。
- recipient 级重试。
- 重复 drain 不重发成功项。
- `NOTIFICATION_DELIVERY_DISABLED=true`。
- allowlist。
- 新增事件不会误走采购机器人。
- 采购通知全量回归。

## 10. 数据库与并发测试

- 部分唯一 Current 索引。
- check constraint。
- Task row lock 与 Revision 并发。
- Review 并发。
- Segment 批量版本冲突全事务回滚。
- worker 使用 SKIP LOCKED 不重复 claim。
- 死锁重试策略。
- transaction timeout 与用户错误映射。

测试必须在隔离 PostgreSQL，不使用生产或日常开发库。

## 11. Schema 发布测试

### 11.1 合成矩阵

构造：

- 采购订单、预算、反馈、User/UserRole、附件、outbox recipient 和 CardKit 跟踪数据。
- 已有 User 尚无 Account/Person、已有完整映射和重复执行三种共享身份初始化场景。
- 缺 openId、重复 unionId、一个身份指向多个 Account 等硬失败场景。
- 空项目管理数据集，验证新 schema 不依赖旧 Project/Task 表。
- 静态和 schema 检查确认不存在 `legacySource*`、migration map 或旧项目管理 enum。

### 11.2 生产快照演练

- 共享身份 dry-run 无写入，APPLY 可重复执行且计数稳定。
- 新项目管理表、enum、索引、外键和 check 与目标 schema 一致。
- 采购、反馈、用户、角色、附件、outbox/recipient 和 CardKit 跟踪数据数量、关系和稳定字段 hash 对账一致。
- 新 Task 只由测试中的显式创建操作产生，不存在旧对象自动导入。
- 空库与包含共享数据的快照都能从 migration history 部署成功。
- 恢复备份耗时符合窗口。

## 12. UI E2E 主流程

### 12.1 Task

1. 创建独立 Task Draft。
2. 创建带 Tag 的 Task。
3. 编辑初始 Milestone 链。
4. 激活，首个 Milestone Active。
5. 提交 Review，Reviewer Approved。
6. 下一 Milestone Active。
7. 创建 Revision、比较、审批、生效。
8. 确认 Termination。
9. 归档。

### 12.2 Resource

1. 批量创建 Planned Segment。
2. 拖拽并产生冲突。
3. 查看解释。
4. 调整并解决。
5. 到期后部分确认。
6. 生成 Actual 并比较。

### 12.3 通知

1. 业务操作产生站内通知。
2. 未读数更新。
3. 打开并跳转。
4. 更新飞书偏好。
5. 无权对象不泄露。

## 13. UI 状态覆盖

所有新增页面：

- loading、empty、error、success、disabled。
- 超长文字、大数据、无 Tag。
- permission read-only。
- Draft、Active、Revised、Completed、Cancelled、Timeout、Archived。
- 网络慢和重复点击。
- 桌面 `1440x1000`。
- Pixel 5。
- 无意外横向滚动。
- 无 Next error overlay、uncaught console error。

关键拖拽必须测试键盘替代操作。

## 14. 性能门槛

在约定基准数据：

- 10,000 Task。
- 100,000 Work Segment。
- 单 Task 50 个版本、每版 100 Node。
- 100,000 站内通知。

建议目标：

| 场景 | 目标 |
|---|---|
| Task 列表首屏服务端 p95 | < 800ms |
| Task 工作台首屏 p95 | < 1.2s |
| 14 天资源时间轴 p95 | < 1.5s |
| 版本比较 p95 | < 1.0s |
| 单人 90 天冲突扫描 | < 2s |
| 普通 action DB 事务 p95 | < 500ms |

网络与浏览器总体验另行记录。未达标必须有 query plan、索引或分页改进，不能只提高超时。

## 15. 安全测试

- 越权读取/写入和 ID 枚举。
- 批量 ID 混入越权对象。
- 附件路径穿越和 MIME/size。
- XSS：Milestone 文本、Revision reason、审计和站内通知。
- CSRF/Origin 与 Server Action。
- 飞书回调身份映射。
- 日志脱敏。
- 审计 append-only 权限。
- 禁用 Account 会话失效。

## 16. 发布门禁

必须运行：

```bash
npm run check
npm run test:domain
npm run test:e2e
npm run build
npx prisma migrate diff --from-migrations prisma/migrations --to-schema prisma/schema.prisma --exit-code
```

新增 `test:domain` 后同步 package-lock。若未新增该脚本，则领域测试必须被 `test:e2e` 明确收集，并在测试报告说明。

上线额外要求：

- 两次 schema 发布演练。
- 一次恢复演练。
- 采购完整回归。
- 业务 UAT。
- 无未解决 P0/P1 缺陷。

## 17. UAT 签字清单

产品负责人确认：

- 系统不存在 Project 实体，所有业务对象为 Task，分类使用 Tag。
- Task 可独立。
- Revision/Review/Termination 语义。
- 旧流程已删除。
- 不出现旧数据导入、legacy 标记或旧项目管理入口。

技术负责人确认：

- 约束、事务、并发。
- schema migration/rollback。
- 监控和通知安全。

测试负责人确认：

- 主路径、权限拒绝、异常、移动端。
- 对账与采购回归。

运维确认：

- 备份恢复。
- 维护窗口。
- worker/outbox。
- 上线值守。
