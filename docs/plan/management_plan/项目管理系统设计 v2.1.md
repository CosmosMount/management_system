# 项目管理系统设计 v2\.1

# 文档说明

本文档用于完整定义项目管理系统 v2 的核心对象、执行规则、人力资源管理方式、账号体系与通知机制，并说明该系统在不同场景下的使用方式。

本文档后续还将结合《开源分析》中的功能要求，对系统能力进行逐项评估，明确当前方案能够直接实现、需要扩展实现以及暂不支持的功能。

---

# Project

Project 是用于组织和管理多个 Task 的上层容器。

Project 本身不直接参与 Task 的执行状态计算，其主要作用是将具有共同业务目标、组织归属或时间范围的多个 Task 集合在一起，并为这些 Task 提供统一的成员、权限和元数据管理。

1. 一个 Project 可以包含任意数量的 Task。

2. 一个 Task 最多属于一个 Project。

3. Task 可以在不属于任何 Project 的情况下独立存在。

4. Project 的删除不得直接删除其包含的 Task，除非用户明确选择级联删除。

5. Project 至少应包含名称、负责人、成员列表、创建时间和当前状态。

6. Project 可以包含开始时间、结束时间、描述、标签、附件和归档状态等附属信息。

7. Project Status 至少包括： 

    - Active

    - Completed

    - Archived

    - Cancelled

# Task

Task 是系统中的基本业务管理对象，用于描述一项完整业务从开始到结束的计划与执行过程。

一个 Task 由多个 Node 按照唯一顺序组成一条有向链。Node 链用于描述 Task 的当前计划、历史计划及计划修订过程。

当前版本中，一个 Task 被定义为最小的独立业务执行单元，不支持拆分为多个可以独立执行和独立终止的子 Task。因此，Task 内部不存在并行 Node、条件分支或多条执行路径。

1. 一个 Node 必须且只能属于一个 Task。

2. 一个 Task 中的所有 Node 必须具有唯一且确定的顺序。

3. 每个 Node 最多具有一个直接前驱 Node 和一个直接后继 Node。

4. 一个 Task 不允许形成分支、循环或多个并行 Node 链。

5. 一个 Task 必须以 Milestone 作为第一个有效计划节点。

6. 一个 Task 必须且只能包含一个有效的 Termination。

7. Termination 必须位于当前有效 Node 链的最后。

8. 任意时刻，一个未结束的 Task 最多只能存在一个当前有效 Milestone。

9. Task 的实际推进由 Node 的验收和 Revision 操作决定，不由时间自动推进。

10. Task 可以关联任意数量的 Work Segment，但 Work Segment 不属于 Node 链。

11. Task 至少应包含名称、描述、负责人、创建时间、当前状态和 Node 链。

12. Task 可以包含优先级、标签、所属 Project、附件、参与人员和备注等附属信息。

Task Status 至少包括：

- Draft

- Active

- Completed

- Failed

- Cancelled

- Timeout

- Archived

# Node

Node 表示 Task 生命周期中的一个计划节点，用于描述 Task 当前阶段的目标、计划修订或最终结束结果。

Node 不是独立 Task，也不表示可以被单独调度的子任务。Node 仅用于构成 Task 的线性计划结构，并记录该计划结构随时间发生的演化。

Node 的核心信息由目标或操作内容、时间信息和判定条件组成，并可以附带负责人、参与人员、附件、备注和关联 Work Segment 等信息。

系统定义三种 Node 类型：

- Milestone

- Revision

- Termination

所有 Node 至少包含以下信息：

1. Node 唯一标识。

2. Node 类型。

3. 所属 Task。

4. Node 在当前链中的顺序。

5. 创建时间。

6. 创建人。

7. 当前状态。

8. 业务描述。

9. 修改历史。

Node Status 至少包括：

- Pending

- Active

- Completed

- Revised

- Cancelled

其中：

1. Pending 表示 Node 尚未成为当前执行节点。

2. Active 表示 Node 当前有效并正在等待完成或处理。

3. Completed 表示 Node 已按照规定条件完成。

4. Revised 表示 Node 所代表的原计划已被 Revision 替代。

5. Cancelled 表示 Node 因 Task 取消或其他明确原因不再继续执行。

## Milestone

Milestone Node 表示当前执行计划中的一个阶段性目标。

Milestone 用于描述当前阶段需要完成的工作内容，并定义对应的完成条件、预期完成时间和验收要求。

Milestone 描述的是当前有效执行计划，而不是具体执行过程。人员每天或每段时间进行的具体工作应由 Work Segment 记录，而不应直接写入 Milestone 的执行状态。

![image\.png](图片和附件/image%201.png)

每个 Milestone 至少包含以下信息：

1. 目标描述。

2. 完成条件。

3. 预期完成时间。

4. 当前状态。

5. 验收要求。

6. 验收结果。

Milestone 应满足以下约束：

1. 每个 Milestone 必须具有明确且可理解的目标描述。

2. 每个 Milestone 必须具有明确的预期完成时间。

3. 每个 Milestone 必须具有可以被判断或验收的完成条件。

4. Milestone 只有在满足完成条件并通过验收后，才可以被标记为 Completed。

5. Milestone 被标记为 Completed 后，Task 才可以进入下一 Node。

6. Milestone 不允许因为到达预期完成时间而自动完成。

7. Milestone 到达预期完成时间但尚未完成时，应被标记为逾期，并由相关负责人决定是否创建 Revision。

8. 已经进入执行过程的 Milestone 不得直接修改目标内容、完成条件、预期完成时间或在 Node 链中的顺序。

9. 对 Milestone 的目标、完成条件、时间或顺序进行实质性修改时，必须通过 Revision 创建新的计划版本。

10. Milestone 的非语义附属信息可以直接修改，包括备注、附件、标签和展示信息。

11. 对附属信息的修改不得改变 Milestone 原有的业务含义、完成判定或时间安排。

12. 一个 Milestone 可以关联任意数量的 Work Segment。

13. Work Segment 的完成不代表 Milestone 自动完成。

14. Milestone 的完成也不要求其关联的所有 Work Segment 必须结束。

---

Milestone Review

Milestone Review 表示对 Milestone 完成情况进行正式验收的过程和结果。

Milestone Review 用于区分“工作已经被执行”和“阶段目标已经满足”两个不同概念。只有验收通过的 Milestone 才能够推动 Task 进入下一 Node。

Milestone Review 至少包含以下信息：

1. 被验收的 Milestone。

2. 验收人。

3. 验收时间。

4. 验收结果。

5. 验收说明。

6. 相关附件或证据。

Review Result 至少包括：

- Pending

- Approved

- Rejected

- Revision Required

Milestone Review 应满足以下约束：

1. Milestone 未提交验收时，Review Result 为 Pending。

2. Approved 表示 Milestone 已满足完成条件，可以标记为 Completed。

3. Rejected 表示 Milestone 当前未满足完成条件，应继续执行原 Milestone。

4. Revision Required 表示原 Milestone 已不适合作为当前计划，应创建 Revision。

5. 验收结果不得直接覆盖历史记录。

6. 同一个 Milestone 可以存在多次验收记录。

7. 最终有效验收结果应以时间上最新且未撤销的验收记录为准。

8. 验收权限可以由 Task、Project 或团队权限配置决定。

## Revision

Revision Node 表示当前执行计划已经无法继续满足项目实际情况，因此 Task 需要对当前 Milestone及其后续计划进行修订。

Revision 表示计划演化，而不是执行暂停。Revision 的作用是保留旧计划、记录修订原因，并建立一条新的有效计划链。

Revision 不直接修改已经存在的历史 Node，而是在保留旧 Node 和原有关系的基础上，建立新的后续 Node 关系。

![image\.png](图片和附件/image.png)

满足以下任一情况时，应创建 Revision：

1. 当前 Milestone 无法按照预期时间完成，需要修改预期完成时间。

2. 当前 Milestone 的目标已经失去业务意义。

3. 当前 Milestone 的完成条件发生实质性变化。

4. 当前 Milestone 需要被新的 Milestone 替代。

5. 当前 Milestone 或后续 Milestone 的顺序需要调整。

6. 当前计划中需要增加或删除 Milestone。

7. 项目的业务范围、技术方案或资源条件发生重大变化。

8. Milestone Review 的结果为 Revision Required。

9. Task 的原计划已经无法继续作为实际执行依据。

Revision 至少应包含以下信息：

1. 修订原因。

2. 被修订的起始 Node。

3. 修订前的计划版本。

4. 修订后的计划版本。

5. 修订人。

6. 修订时间。

7. 受影响的 Milestone。

8. 可选的审批结果和备注。

Revision 应满足以下约束：

1. Revision 不表示当前 Milestone 已完成。

2. Revision 必须明确记录计划修订原因。

3. Revision 必须明确指出修订从哪个 Milestone 或 Termination 开始生效。

4. Revision 生效后，被替代的当前 Milestone 应标记为 Revised。

5. Revision 之后的第一个有效 Milestone 自动成为新的当前计划节点。

6. Revision 不允许作为未结束 Task 的最后一个有效 Node。

7. Revision 后必须存在新的 Milestone 或新的 Termination。

8. Revision 之前的 Node 不得被物理删除。

9. Revision 之前的 Node 关系和历史计划版本应被完整保留。

10. Revision 可以替换当前 Milestone，也可以替换当前 Milestone 之后的全部或部分计划。

11. Revision 不得修改已经 Completed 的历史 Milestone所代表的既成事实。

12. Revision 可以修改 Completed Milestone 之后尚未执行的计划。

13. Revision 应形成新的计划版本，以支持后续对不同计划版本进行比较。

14. 旧计划版本默认不作为当前 Task 的执行路径，但可以在历史视图中查看。

15. 同一个 Task 可以进行任意次数的 Revision。

16. 每次 Revision 必须能够独立追溯修订原因、修订范围和修订结果。

## Plan Version

Plan Version 表示 Task 在某一时间点上有效的完整 Node 计划。

每次创建 Task 时，系统生成初始 Plan Version。每次 Revision 生效后，系统生成新的 Plan Version。

Plan Version 用于保存 Task 的历史计划结构，避免 Revision 后原有 Node 链被覆盖或丢失。

Plan Version 应满足以下约束：

1. 一个 Task 至少存在一个 Plan Version。

2. 一个 Task 任意时刻只能存在一个 Current Plan Version。

3. Revision 生效后，新版本成为 Current Plan Version。

4. 旧 Plan Version 自动成为 Historical Plan Version。

5. Historical Plan Version 不允许直接修改。

6. 每个 Plan Version 必须记录创建时间、创建原因和对应 Revision。

7. 每个 Plan Version 必须能够完整还原当时的 Node 顺序和 Node 内容。

8. 不同 Plan Version 可以引用相同的历史 Node。

9. 新 Plan Version 中被替代的 Node 可以由新的 Node 接替。

10. Plan Version 的存在不得导致 Work Segment 被自动复制或删除。

---

## Termination

Termination Node 表示 Task 生命周期结束。

当 Task 到达有效 Termination 并完成结束确认后，Task 不再继续执行，也不允许在当前 Plan Version 中新增后续 Node。

一个 Task 必须且只能存在一个当前有效的 Termination。

Termination Status 至少包括：

- Success

- Failed

- Cancelled

- Timeout

Termination 应满足以下约束：

1. Termination 必须位于当前有效 Node 链的最后。

2. Termination 必须记录 Task 的最终结束状态。

3. Termination 可以记录结束原因、结束时间、负责人和总结信息。

4. Success 表示 Task 已按照最终有效计划完成。

5. Failed 表示 Task 未能达到预期业务结果，并被明确终止。

6. Cancelled 表示 Task 因外部决策或业务变化被主动取消。

7. Timeout 表示 Task 因超过允许时间而结束。

8. Termination 生效后，Task Status 应同步更新。

9. 已经生效的 Termination 不允许直接删除。

10. 未生效且位于未来计划中的 Termination 可以通过 Revision 替换。

11. 已结束的 Task 原则上不允许恢复执行。

12. 若结束后出现新的业务需求，应创建新的 Task，并可以引用原 Task。

Task Execution

Task 按照当前 Plan Version 中的 Node 顺序推进。

Task 的推进依据是 Milestone 的完成条件和验收结果，而不是时间到达。预期完成时间仅用于计划、提醒、逾期识别和资源分析。

Task Execution 应满足以下规则：

1. Task 创建后，第一个 Milestone 成为当前 Active Milestone。

2. 当前 Milestone 满足完成条件并通过验收后，状态变为 Completed。

3. 当前 Milestone 完成后，下一有效 Node 成为当前 Node。

4. 下一有效 Node 为 Milestone 时，该 Milestone 状态变为 Active。

5. 下一有效 Node 为 Revision 时，系统按照 Revision 生成的新 Plan Version 继续执行。

6. 下一有效 Node 为 Termination 时，Task 进入结束确认流程。

7. 不允许跳过未完成的当前 Milestone直接完成后续 Milestone。

8. 不允许同时存在多个 Active Milestone。

9. 到达 Milestone 预期完成时间不会自动改变 Milestone 状态。

10. Milestone 逾期后，系统应发送提醒，但是否 Revision 由负责人决定。

11. 若当前计划无法继续执行，应创建 Revision，而不是直接修改 Node 链。

12. Work Segment 的创建、结束或确认不得自动推动 Task。

13. Task 的状态应由当前 Node、验收结果和 Termination 共同决定。

---

Task Modification

Task Modification 表示对 Task 当前有效计划进行结构性或语义性调整。

任何涉及 Milestone 目标、完成条件、预期完成时间、Node 顺序或计划范围的修改，都必须通过 Revision 实现。

以下情况必须创建 Revision：

1. 当前 Milestone 未达到预期目标，并需要更换目标。

2. 当前 Milestone 需要延期。

3. 当前 Milestone 的完成时间需要提前。

4. 当前 Milestone 的完成条件需要修改。

5. 当前 Milestone 需要拆分为多个 Milestone。

6. 多个 Milestone 需要合并。

7. 需要新增未来 Milestone。

8. 需要删除未来 Milestone。

9. Milestone 的执行顺序需要调整。

10. 原 Termination 的结束时间或结束条件需要修改。

11. Task 的整体规划发生变化。

以下信息允许不通过 Revision 直接修改：

1. 拼写和格式错误。

2. 不改变业务含义的描述优化。

3. 备注。

4. 标签。

5. 附件。

6. 展示样式。

7. 参与人员的附属说明。

8. 不影响 Node 顺序、完成条件和计划时间的其他信息。

---

Milestone Refinement

Milestone Refinement 表示在不改变原 Milestone 核心目标、完成条件和预期完成时间的前提下，为当前 Milestone 补充更细粒度的工作说明。

Milestone Refinement 不应通过在 Node 链中随意插入新的 Milestone 实现。具体到人员和时间段的工作分配，应优先通过 Planned Segment 表达。

只有当补充内容本身具有独立验收条件和独立计划时间，并且会影响 Task 的推进顺序时，才应通过 Revision 将其创建为新的 Milestone。

Milestone Refinement 应满足以下规则：

1. 仅用于补充当前 Milestone 的详细说明。

2. 不得改变 Milestone 的核心目标。

3. 不得改变 Milestone 的完成条件。

4. 不得改变 Milestone 的预期完成时间。

5. 不得改变 Node 链顺序。

6. 人员在某段时间内完成的具体工作应记录为 Work Segment。

7. 若补充内容需要独立验收，应通过 Revision 创建新的 Milestone。

8. 若补充内容导致后续时间线变化，应通过 Revision 修改计划。

---

Delay

Delay 表示 Milestone 的实际执行进度落后于当前计划。

Delay 是一种计划偏差，不应作为独立的第四种 Node 类型。是否需要创建 Revision，应根据 Delay 是否导致当前计划发生实质变化决定。

Delay 应按照以下规则处理：

1. 出现轻微进度延后但预期完成时间不变时，仅记录风险、提醒或备注，不创建 Revision。

2. 预期完成时间需要修改时，必须创建 Revision。

3. 当前 Milestone 延期导致后续 Milestone 时间发生变化时，必须创建 Revision。

4. Revision 应记录原计划时间、新计划时间和延期原因。

5. 后续 Node 的时间不得由系统无条件统一后移。

6. 系统可以提供批量顺延功能，但必须由负责人确认后通过 Revision 生效。

7. 后续 Milestone 是否顺延，应根据各 Milestone 的依赖关系、资源安排和实际情况决定。

8. Delay 数据应能够用于统计延期次数、延期时长和主要延期原因。

# Human Resource Tracking

Human Resource Tracking 用于描述团队成员在不同时间段内的工作安排和实际投入情况。

该模块的目标不是进行考勤、工时审计或个人绩效评估，而是帮助负责人理解人员当前工作、未来计划、资源冲突和计划执行偏差。

Human Resource Tracking 应尽可能降低成员的使用负担。系统应优先通过计划复用、批量确认、拖拽调整、自动填充和默认值等方式完成信息记录，而不是要求成员频繁填写详细工作日志。

Human Resource Tracking 应支持回答以下问题：

1. 当前每个人主要在完成哪些工作。

2. 未来一段时间每个人计划完成哪些工作。

3. 某个 Task 当前有哪些人员参与。

4. 某个 Node 当前有哪些人员参与。

5. 某个成员是否还有可以分配的时间。

6. 某个成员是否同时承担多个冲突工作。

7. 是否存在人员过度分配。

8. 是否存在人员计划空缺。

9. 计划安排与实际执行之间是否存在明显偏差。

10. 某个 Task 在一段时间内消耗了多少人员投入。

11. 某个成员在多个 Task 之间如何分配时间。

12. 哪些 Milestone 存在人员配置不足的风险。

---

## Work Segment

Work Segment 表示某一个人在一段明确时间内计划进行或实际进行的一项工作。

一个 Work Segment 只描述一个人的工作安排或实际投入。如果同一项工作由多个人共同完成，系统应分别为每个人创建 Work Segment，但可以通过批量操作一次完成创建。

Work Segment 是 Human Resource Tracking 模块中的独立对象。它可以引用 Project、Task 和 Node，但不属于 Task 的 Node 链，也不会直接参与 Task 和 Milestone 的状态计算。

一个 Work Segment 至少包含以下信息：

1. 所属人员。

2. Segment 类型。

3. 开始时间。

4. 结束时间。

5. 工作内容。

6. Allocation。

7. 当前状态。

8. 创建时间。

9. 创建人。

Work Segment 可以包含以下附属信息：

- Project。

- Task。

- Node。

- 人员在该工作中的 Role。

- Priority。

- 预计产出。

- 实际产出。

- Completion。

- 工作标签。

- 调整原因。

- 备注。

- 来源 Planned Segment。

- 创建人。

- 最后修改人。

- 修改历史。

Work Segment 应满足以下约束：

1. 一个 Work Segment 必须且只能属于一个人。

2. 一个 Work Segment 必须具有明确的开始时间和结束时间。

3. Work Segment 的结束时间必须晚于开始时间。

4. 一个 Work Segment 必须具有工作内容描述。

5. 一个 Work Segment 可以关联一个 Project。

6. 一个 Work Segment 可以关联一个 Task。

7. 一个 Work Segment 最多关联一个具体 Node。

8. Work Segment 关联的 Node 必须属于其关联的 Task。

9. 一个 Task 或 Node 可以关联任意数量的 Work Segment。

10. 一个人可以同时存在多个相互重叠的 Work Segment。

11. Work Segment 重叠不直接表示数据错误。

12. 系统应根据重叠时间和 Allocation 判断是否存在过度分配。

13. Work Segment 的新增、删除或调整不会直接修改 Task 或 Node。

14. Work Segment 不参与 Milestone 完成条件的自动判断。

15. Work Segment 应保留必要的修改历史。

16. Task 关联不是 Work Segment 存在的前提条件。

17. 未关联 Task 的 Work Segment 可以用于记录行政、培训、会议或其他非项目工作。

18. Work Segment 的时间范围可以跨越多个自然日。

19. 系统可以根据团队规则限制单个 Work Segment 的最大跨度。

---

## Allocation

Allocation 表示某个人在 Work Segment 所覆盖时间段内，计划或实际投入该项工作的时间比例。

Allocation 用于处理同一人员在同一时间段内同时参与多个工作的问题。

Allocation 应满足以下规则：

1. Allocation 使用百分比表示。

2. Allocation 的有效范围为大于 0% 且不超过 100%。

3. 同一人员在任意时间点的多个 Planned Segment Allocation 总和可以超过 100%，但系统必须产生过度分配警告。

4. 同一人员在任意时间点的多个 Actual Segment Allocation 总和可以超过 100%，但系统应标记为可能存在记录重叠或并行工作。

5. Allocation 不直接等于实际工时。

6. Workload 可以由 Segment 时长与 Allocation 的乘积估算。

7. 系统不得仅根据 Allocation 自动评价个人绩效。

8. Allocation 的修改应保留历史记录。

---

## Role

Role 表示人员在某个 Work Segment 所描述工作中的职责类型。

Role 用于区分同一人员在不同 Task 或 Node 中承担的责任，但不等同于系统权限角色。

Role 可以包括：

- Owner

- Lead

- Developer

- Designer

- Reviewer

- Support

- Observer

- Custom

Role 应允许团队根据实际业务自定义。

---

## Priority

Priority 表示 Work Segment 或 Task 在资源冲突时的相对处理优先级。

Priority 仅用于计划分析、冲突提示和视图排序，不应自动取消或调整其他工作。

Priority 至少包括：

- Critical

- High

- Medium

- Low

---

## Completion

Completion 表示 Actual Segment 中记录的工作内容在该时间段结束时的相对完成程度。

Completion 仅用于描述该 Work Segment 所对应工作内容的进展，不表示关联 Milestone 的完成度，也不得自动改变 Milestone 状态。

Completion 可以使用以下任一方式实现：

1. 0% 至 100% 的数值。

2. Not Started、In Progress、Completed 等离散状态。

3. 团队自定义的进展状态。

若使用百分比，Completion 应满足以下规则：

1. Completion 的有效范围为 0% 至 100%。

2. 100% 仅表示该 Segment 中记录的工作内容已经完成。

3. Completion 不得自动聚合为 Milestone 完成状态。

4. 多个 Segment 的 Completion 不应直接进行无权平均。

5. 系统可以提供统计参考，但最终 Milestone 完成仍由验收决定。

---

Relationship with Project, Task and Node

Project、Task 和 Node 描述的是业务计划、计划结构及其演化过程。

Person 和 Work Segment 描述的是人员在时间维度上的计划投入和实际投入。

Work Segment 与 Project、Task 和 Node 之间是引用关系，而不是执行链中的从属关系。

其关系可以表示为：

```Plain Text
Project
└── Task
    └── Current Plan Version
        └── Node Chain
            ├── Milestone
            ├── Revision
            └── Termination

Person
└── Work Segment
    ├── Optionally Reference Project
    ├── Optionally Reference Task
    └── Optionally Reference Node
```

该关系应满足以下规则：

1. Task 被 Revision 修改时，Work Segment 不会被自动删除。

2. Task 被 Revision 修改时，系统应提示用户检查受影响的 Planned Segment。

3. Work Segment 被调整时，Task 的 Node 链不会自动变化。

4. Node 完成不代表其关联的所有 Work Segment 已经结束。

5. Actual Segment 被确认不代表其关联的 Milestone 已经通过验收。

6. 一个 Node 可以由多个人在不同时间段内共同完成。

7. 一个人可以在同一时期参与多个 Task 或 Node。

8. Work Segment 可以引用 Historical Plan Version 中的 Node。

9. 当 Work Segment 引用的 Node 被标记为 Revised 时，系统应提示用户重新确认关联关系。

10. 系统不得自动将关联 Revised Node 的 Work Segment 删除或迁移到新 Node。

11. 用户可以手动将 Planned Segment 重新关联至 Revision 后的新 Milestone。

12. Actual Segment 应保留其发生时所关联的原 Node，不应因后续 Revision 被重写。

---

Work Segment Type

Work Segment 分为 Planned Segment 和 Actual Segment 两种类型。

Planned Segment 用于描述人员计划投入，Actual Segment 用于描述已经发生的人员投入。

Work Segment Type 包括：

- Planned Segment

- Actual Segment

---

Planned Segment

Planned Segment 表示某个人未来或当前计划投入到某项工作的时间范围。

Planned Segment 的主要用途是人员安排、任务规划和资源冲突分析。Planned Segment 可以由组长、项目负责人或成员本人创建。

Planned Segment 应满足以下规则：

1. Planned Segment 表示工作安排，不表示工作已经发生。

2. Planned Segment 可以由具有权限的负责人或成员本人创建。

3. Planned Segment 可以修改开始时间、结束时间、工作内容、Allocation、Priority 和 Role。

4. Planned Segment 的修改应保留必要的历史记录。

5. Planned Segment 可以被拆分为多个 Planned Segment。

6. 拆分后的 Planned Segment 应保留对原 Segment 的来源引用。

7. 多个相邻且业务内容一致的 Planned Segment 可以合并。

8. Planned Segment 可以转换为一个或多个 Actual Segment。

9. Planned Segment 可以被取消。

10. Planned Segment 被取消后不得物理删除。

11. 被取消的 Planned Segment 默认不显示在主要时间线上，但可以在历史记录中查看。

12. Planned Segment 到达结束时间后，应进入待确认状态。

13. Planned Segment 不得因到达结束时间自动转换为 Actual Segment。

14. 是否要求成员逐条确认可以由团队配置。

15. Planned Segment 可以批量创建、批量移动和批量确认。

16. Planned Segment 可以通过拖拽方式调整时间。

17. Planned Segment 可以根据 Task、Node 或历史安排自动填充默认内容。

18. Planned Segment 所关联的 Node 被 Revision 替代时，应提示计划创建人重新确认。

19. Planned Segment 被重新关联至新 Node 时，应保留原关联历史。

20. Planned Segment 的 Allocation 应参与未来人员负载分析。

Planned Segment Status 至少包括：

- Planned

- In Progress

- Pending Confirmation

- Confirmed

- Cancelled

---

Actual Segment

Actual Segment 表示某个人在某个时间段内实际进行过的工作。

Actual Segment 仅说明该人员投入已经发生，不表示其关联的 Task、Node 或 Milestone 已经完成。

Actual Segment 可以通过以下方式产生：

1. 由 Planned Segment 确认转换。

2. 由 Planned Segment 部分转换。

3. 成员直接创建，用于记录未提前规划的工作。

4. 由负责人根据实际情况补充创建。

5. 通过团队允许的数据来源自动生成后由成员确认。

Actual Segment 应满足以下规则：

1. Actual Segment 必须记录实际开始时间和实际结束时间。

2. Actual Segment 必须记录实际工作内容。

3. Actual Segment 可以记录实际产出或结果摘要。

4. Actual Segment 可以记录 Completion。

5. Actual Segment 可以关联 Project、Task 和 Node。

6. Actual Segment 从 Planned Segment 产生时，必须保留对原 Planned Segment 的引用。

7. 原 Planned Segment 不应被物理删除。

8. Planned Segment 与 Actual Segment 应能够进行计划和实际对比。

9. Actual Segment 可以修改，但系统必须保留修改历史。

10. Actual Segment 不得自动修改 Node 的完成状态。

11. Actual Segment 不要求填写详细日报。

12. 默认情况下，成员只需要确认实际时间、Task、工作内容和必要的产出摘要。

13. 当 Actual Segment 与 Planned Segment 基本一致时，成员应能够通过一次操作完成确认。

14. 当实际投入只覆盖 Planned Segment 的一部分时，应允许部分确认。

15. 一个 Planned Segment 可以产生多个 Actual Segment。

16. 多个 Planned Segment 可以根据实际情况关联到同一个 Actual Segment，但系统应保留所有来源关系。

17. Actual Segment 的 Allocation 应参与实际人员负载统计。

18. Actual Segment 所关联的历史 Node 不应因 Revision 被自动修改。

19. Actual Segment 可以在创建后补充 Task 或 Node 关联。

20. Actual Segment 的删除应采用逻辑删除，并保留审计记录。

---

Planned and Actual Comparison

Planned and Actual Comparison 用于比较人员原计划投入与实际投入之间的差异。

该比较用于项目复盘、资源规划和流程优化，不应被直接用于个人绩效评价。

系统至少应支持以下比较：

1. 计划开始时间与实际开始时间。

2. 计划结束时间与实际结束时间。

3. 计划时长与实际时长。

4. 计划 Allocation 与实际 Allocation。

5. 计划工作内容与实际工作内容。

6. 计划产出与实际产出。

7. 计划关联 Task 与实际关联 Task。

8. 计划关联 Node 与实际关联 Node。

9. 未执行的 Planned Segment。

10. 未提前规划的 Actual Segment。

11. 因 Revision 产生的计划调整。

12. 人员在一段时间内的计划负载与实际负载。

---

Resource Conflict

Resource Conflict 表示同一人员在同一时间范围内存在多个 Work Segment，且其 Allocation、时间或优先级关系可能导致无法按照计划完成全部工作。

Resource Conflict 是系统提示，不是自动判定的管理结论。

满足以下任一情况时，系统可以产生 Resource Conflict：

1. 同一人员在某个时间点的 Planned Allocation 总和超过 100%。

2. 同一人员在同一时间段存在多个 Allocation 未填写的 Planned Segment。

3. 多个 Critical 或 High Priority Segment 发生时间重叠。

4. 同一人员在多个不同 Project 中被安排为 Owner 或 Lead，且时间范围高度重叠。

5. 某个 Milestone 的预期完成时间临近，但关联人员投入明显不足。

6. Planned Segment 与成员不可用时间发生冲突。

7. Revision 导致新的人员安排与原计划重叠。

8. Actual Segment 显示人员长期超过计划负载。

系统发现 Resource Conflict 后应：

1. 向相关负责人提供提示。

2. 展示冲突时间范围。

3. 展示冲突 Segment。

4. 展示各 Segment 的 Priority、Allocation、Role 和关联 Task。

5. 允许负责人手动调整。

6. 不得未经确认自动删除或移动 Work Segment。

7. 可以提供自动调整建议，但必须由用户确认后生效。

---

Account

Account 表示用户访问项目管理系统时使用的身份对象。

系统应同时支持邮箱账号和飞书账号，并允许同一个 Account 绑定多个登录渠道。

系统支持以下登录方式：

- 飞书登录。

- 邮箱与密码登录。

Account 应满足以下规则：

1. 每个 Account 必须具有唯一的系统用户标识。

2. 邮箱地址在系统范围内必须唯一。

3. 飞书用户标识在系统范围内必须唯一。

4. 一个 Account 可以同时绑定邮箱和飞书。

5. 邮箱登录与飞书登录进入同一个 Account 时，不应创建重复用户。

6. 新成员可以先通过邮箱注册，后续再绑定飞书。

7. 已有飞书成员可以直接通过飞书登录。

8. 账号绑定和解绑操作必须经过身份验证。

9. 邮箱密码必须使用安全密码哈希保存，不得以明文形式存储。

10. 系统应支持密码重置、登录设备管理和异常登录提示。

11. 系统应支持禁用 Account，但禁用操作不得删除其历史数据。

12. 成员退出团队后，其 Account、Work Segment 和操作历史应继续保留。

13. Person 与 Account 应作为不同概念处理。

14. Account 表示系统登录身份，Person 表示组织中的人员对象。

15. 一个 Person 通常关联一个 Account，但系统应允许暂未注册 Account 的 Person 存在。

---

Notification

Notification 表示系统针对任务变化、计划修订、验收、资源冲突和账号事件向用户发送的信息。

系统支持飞书和邮箱两种通知渠道。

Notification Channel 包括：

- Feishu

- Email

- In\-App

Notification 应满足以下规则：

1. 已绑定飞书的用户可以接收飞书通知。

2. 已绑定邮箱的用户可以接收邮箱通知。

3. 用户可以关闭非必要邮箱通知。

4. 用户关闭邮箱通知后，账号安全类邮件仍可按照系统安全策略发送。

5. 用户可以分别配置不同事件的通知渠道。

6. 系统应避免同一事件通过多个渠道产生过量重复通知。

7. 重要 Revision、Milestone Review 和 Resource Conflict 可以同时通过多个渠道发送。

8. Notification 应记录发送时间、接收人、渠道和发送状态。

9. 发送失败的 Notification 应支持重试。

10. 用户应能够在系统内查看历史通知。

11. 项目负责人可以配置 Project 级默认通知规则。

12. 团队管理员可以配置团队级强制通知规则。

系统至少应支持以下通知事件：

1. Milestone 即将到期。

2. Milestone 已经逾期。

3. Milestone 提交验收。

4. Milestone 验收通过。

5. Milestone 验收拒绝。

6. Milestone 需要 Revision。

7. Revision 已创建。

8. Revision 已生效。

9. Planned Segment 即将开始。

10. Planned Segment 到达结束时间并等待确认。

11. Resource Conflict 被识别。

12. 用户被分配到新的 Task、Node 或 Work Segment。

13. Task 已经 Terminate。

14. Account 出现安全相关事件。

---

Permission

Permission 用于控制用户对 Project、Task、Node、Work Segment、账号和系统配置的访问与修改能力。

权限系统应区分组织权限、Project 权限、Task 权限和对象所有者权限。

系统可以定义以下基础角色：

- System Administrator

- Team Administrator

- Project Owner

- Task Owner

- Member

- Viewer

Permission 应满足以下原则：

1. 用户只能查看其有权限访问的数据。

2. 创建 Revision 应要求用户具有 Task 编辑权限。

3. Milestone Review 应要求用户具有验收权限。

4. 用户默认可以编辑本人创建或属于本人的 Work Segment。

5. 负责人是否可以编辑成员 Work Segment 应由团队权限配置决定。

6. 历史 Plan Version 默认只读。

7. 审计记录不得被普通用户修改。

8. 删除操作应优先采用逻辑删除。

9. 重要操作可以要求二次确认。

10. 权限变化应保留历史记录。

---

Audit History

Audit History 用于记录系统中会影响业务计划、人员安排和权限关系的重要操作。

Audit History 的目标是支持历史追溯、问题定位和计划分析，而不是记录所有无意义的界面操作。

系统至少应记录以下操作：

1. Task 创建、归档和结束。

2. Milestone 创建和状态变化。

3. Revision 创建和生效。

4. Plan Version 创建。

5. Termination 生效。

6. Milestone Review。

7. Work Segment 创建、拆分、合并、修改、确认和取消。

8. Account 绑定和解绑。

9. Permission 修改。

10. Project 成员变化。

每条 Audit History 至少包含：

1. 操作人。

2. 操作时间。

3. 操作对象。

4. 操作类型。

5. 修改前信息。

6. 修改后信息。

7. 可选的修改原因。

---

Interface Representation

系统界面应明确区分业务计划、历史计划、人员计划和实际投入，避免将不同语义的数据混合显示。

建议采用以下视觉规则：

1. 当前 Plan Version 使用主要实线显示。

2. Historical Plan Version 使用较弱颜色、虚线或折叠视图显示。

3. Milestone 使用目标节点样式。

4. Revision 使用明显的计划分叉或版本切换样式，但逻辑数据结构仍保持单链版本。

5. Termination 使用结束节点样式。

6. Planned Segment 使用空心、浅色或虚线时间块。

7. Actual Segment 使用实心时间块。

8. Cancelled Segment 默认隐藏，但允许在历史模式中查看。

9. Revised Milestone 应显示为历史计划，不应与当前 Active Milestone 混淆。

10. Resource Conflict 应在人员时间轴和 Task 视图中同时提供提示。

11. 用户应能够从 Milestone 查看相关 Work Segment。

12. 用户应能够从 Work Segment 跳转到其关联的 Project、Task 和 Node。

13. 用户应能够对不同 Plan Version 进行对比。

14. 用户应能够查看 Revision 前后的 Node、时间和人员安排变化。

---

System Structure

系统整体数据关系由业务计划结构和人员时间结构两部分组成。

业务计划结构用于记录项目、任务和计划版本；人员时间结构用于记录每个人的计划投入与实际投入。

```Plain Text
Project
├── Metadata
├── Members
└── Task
    ├── Metadata
    ├── Current Plan Version
    │   └── Node Chain
    │       ├── Milestone
    │       ├── Revision
    │       └── Termination
    ├── Historical Plan Versions
    ├── Milestone Reviews
    └── Audit History

Person
├── Account
├── Permissions
└── Work Segment
    ├── Planned Segment
    └── Actual Segment
```

---

Design Principles

1. **Plan\-Oriented**：系统优先记录项目计划、计划执行和计划演化，而不是要求成员持续填写详细日报。

2. **Immutable History**：已经生效的计划和执行历史不应被直接覆盖。

3. **Revision\-Based Modification**：涉及目标、时间、条件和顺序的计划修改必须通过 Revision 实现。

4. **Linear Workflow**：每个 Task 的每个 Plan Version 只包含一条线性 Node 链。

5. **Single Active Milestone**：任意时刻，一个未结束 Task 最多只有一个 Active Milestone。

6. **Review\-Driven Execution**：Task 推进由 Milestone Review 驱动，而不是由时间自动驱动。

7. **Plan and Resource Separation**：Task 和 Node 描述业务计划，Work Segment 描述人员投入，两者相互引用但互不直接控制。

8. **Low Recording Burden**：系统应通过默认值、批量操作、计划复用和快速确认降低成员记录负担。

9. **Traceability**：任何计划修订、人员安排和状态变化都应可以追溯。

10. **No Automatic Business Decisions**：系统可以提供提醒、冲突分析和调整建议，但不得未经负责人确认自动改变业务计划。

11. **Logical Deletion**：重要业务对象原则上采用逻辑删除，并保留必要历史。

12. **Extensibility**：当前版本虽然不支持子 Task、并行 Node 和条件分支，但数据结构应避免阻碍未来扩展。
