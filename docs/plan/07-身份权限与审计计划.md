# 身份、权限与审计计划

## 1. 身份边界

### 1.1 Account

Account 表示可以登录系统的身份。本期只允许飞书登录：

- Auth.js 飞书 OAuth 返回身份。
- 通过 unionId/openId 解析 AccountIdentity。
- Account 处于 ACTIVE 才能建立会话。
- Account 可关联一个 Person。

### 1.2 Person

Person 表示组织中的人：

- 可以尚未登录，没有 Account。
- 可以先被分配 Task、Milestone 或 Planned Segment。
- 后续飞书登录后由管理员或受控匹配绑定 Account。
- Account 禁用后历史 Person、Segment、Review 和 Audit 不删除。

本期不实现邮箱、密码或邮件身份。

## 2. 角色体系

### 2.1 系统角色

| 角色 | 范围 | 说明 |
|---|---|---|
| System Administrator | 全局 | 系统配置、角色、受限纠错 |
| Team Administrator | team/techGroup | 管理范围内 Task 与资源 |
| Resource Manager | team/techGroup | 管理他人 Segment、解决冲突 |
| Auditor | 全局或范围 | 只读历史、审计与统计 |

采购原有角色继续保留，不自动获得项目管理权限，除非显式映射到上述角色。

### 2.2 Task 成员角色

| 角色 | 说明 |
|---|---|
| OWNER | 管理 Task 元数据、成员、计划和结束 |
| LEAD | 执行协调，可发起 Revision 和管理计划 |
| MEMBER | 执行 Milestone、管理本人 Segment |
| REVIEWER | Review Milestone 与 Revision |
| VIEWER | 只读 |

同一 Person 可有多个角色；权限取并集，但状态约束仍生效。

### 2.3 Tag 权限

Tag 没有成员角色。创建人可编辑自己创建的 Tag，System/Team Administrator 可管理范围内 Tag；Tag 不提供任何 Task 权限。

## 3. 默认可见性

- Task 只对 TaskMember、范围内 Team Administrator、System Administrator、授权 Auditor 可见。
- 所有 Task 使用同一规则，Tag 不扩大或缩小 Task 可见性。
- Work Segment 默认本人、其 Resource Manager、有关 Task 的 Viewer 仅在 Task 上下文查看“与该 Task 关联的部分”。
- 全局人员时间轴只对 Resource Manager、Team Administrator 和 System Administrator 开放；普通成员只看本人。
- 审计记录按对象查看权限过滤，敏感权限变更仅管理员/Auditor 可见。

## 4. 操作权限矩阵

`✓` 为允许，`条件` 表示还需范围、对象关系与状态判断。

| 操作 | Sys Admin | Team Admin | Task Owner | Lead | Member | Reviewer | Viewer |
|---|---:|---:|---:|---:|---:|---:|---:|
| 查看 Task | ✓ | 条件 | ✓ | ✓ | ✓ | ✓ | ✓ |
| 创建 Task | ✓ | 条件 | - | - | - | - | - |
| 编辑 Task 元数据 | ✓ | 条件 | ✓ | ✓ | - | - | - |
| 管理 Task 成员 | ✓ | 条件 | ✓ | - | - | - | - |
| 激活 Task | ✓ | 条件 | ✓ | - | - | - | - |
| 发起 Revision | ✓ | 条件 | ✓ | ✓ | 条件 | - | - |
| 直接生效 Revision | ✓ | 条件 | 条件 | - | - | - | - |
| Review Revision | ✓ | 条件 | 条件 | - | - | ✓ | - |
| 提交 Milestone 验收 | ✓ | 条件 | ✓ | ✓ | 条件 | - | - |
| Review Milestone | ✓ | 条件 | 条件 | - | - | ✓ | - |
| 确认 Termination | ✓ | 条件 | ✓ | - | - | 条件 | - |
| 管理本人 Segment | ✓ | ✓ | 条件 | 条件 | ✓ | ✓ | ✓ |
| 管理他人 Segment | ✓ | 条件 | - | - | - | - | - |
| 解决 Resource Conflict | ✓ | 条件 | 条件 | - | - | - | - |
| 查看审计 | ✓ | 条件 | ✓ | ✓ | 条件 | ✓ | 条件 |

防自审：

- 默认 Reviewer 不能审批自己提交的 Milestone Review 或 Revision。
- `allowSelfReview` 只能由 System Administrator 在 Task 策略中开启，并写审计。
- 不能因同时拥有 Owner 和 Reviewer 就绕过防自审。

## 5. 授权实现

### 5.1 单一策略入口

```ts
authorize({
  actor,
  action,
  resource,
  context,
})
```

返回 allow/deny 和内部 reason code。用户只看到安全中文提示；日志记录 reason code。

### 5.2 查询过滤

为每类列表提供 `readableWhere(actor)`：

- `taskReadableWhere`
- `segmentReadableWhere`
- `tagReadableWhere`
- `auditReadableWhere`
- `notificationReadableWhere`

详情页使用带 readableWhere 的 `findFirst`，不要先按 ID 查出对象后再在内存判断，以减少存在性泄露。

### 5.3 状态约束

授权允许不代表状态允许。例如 Owner 对 Historical Plan 仍然只读。每个 action 顺序为：

1. 鉴权。
2. 授权。
3. 状态机/不变量。
4. 事务内再校验。

## 6. Account 与 Person 绑定

流程：

1. 飞书同步创建/更新候选 Person。
2. 首次登录按稳定飞书身份查 AccountIdentity。
3. 若存在唯一明确 Person 映射，自动绑定。
4. 若同名、多 openId 或 unionId 冲突，不自动合并，进入管理员待处理。
5. 管理员绑定/解绑需要二次确认并写审计。

不得仅凭姓名或邮箱自动合并。

## 7. 审计模型

### 7.1 必须审计

- Account 禁用、身份绑定/解绑。
- 系统角色、Task 成员和 Tag 变化。
- Task 创建、激活、状态结束、归档、删除。
- Plan Version 创建、Revision 提交/审批/生效/取消。
- Milestone 状态与每次 Review/撤销。
- Termination 确认。
- Segment 创建、修改、拆分、合并、确认、取消、删除、重关联。
- Conflict 确认、解决、忽略。
- 通知偏好强制规则变化。
- 迁移批次和破坏性清理。

### 7.2 字段

- `actorAccountId`、`actorPersonId`
- `action`
- `entityType/entityId`
- `taskId`
- `before/after Json`
- `reason`
- `requestId`
- `source`（WEB/CRON/MIGRATION/SYSTEM）
- `schemaVersion`
- `createdAt`

审计 append-only。普通应用角色没有 UPDATE/DELETE 权限。

### 7.3 隐私和最小化

- 不记录 OAuth token、cookie、飞书 app secret。
- Work Segment before/after 只记录业务字段，不复制附件正文。
- 敏感管理员审计只向 System Administrator/Auditor 展示。
- UI 的审计导出需授权、范围和导出日志。

## 8. 受限纠错

历史不可变不等于无法纠错。受限纠错流程：

- 只有 System Administrator。
- 必填工单号/原因。
- 展示影响对象。
- 生成补偿事件，不修改原审计。
- 若修正已推进的 Approved Review，必须创建新的计划修订或补偿状态，而不是删除 Review。
- 执行前二次确认，执行后站内通知 Task Owner 和 Auditor。

## 9. 安全检查

- 所有 action 参数视为不可信。
- 无权对象统一返回 NOT_FOUND 或 FORBIDDEN，避免枚举。
- 飞书回调操作人重新映射 Account，并复用同一授权策略。
- 附件下载按 Task/Review/Segment 可见性授权。
- 批量操作逐项验证对象归属，禁止混入越权 ID。
- 审计和通知中的链接只使用内部 ID，不暴露文件系统路径。
- 权限缓存变化后立即失效，不允许旧会话长期保留已撤销角色。

## 10. 删除旧权限代码

切换后删除旧 ProjectStage、立项、旧 Task submission/DDL/weekly/risk 对应 permission helper。保留文件中的采购权限不受影响。最终目标是旧 `lib/permissions-progress.ts` 被新策略模块完全取代，而不是同时存在两套判断。
