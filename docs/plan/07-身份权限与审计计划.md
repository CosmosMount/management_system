# 统一身份、权限与审计实现

> 状态（2026-08-04）：账号级项目访问状态已按 [移除账号级项目访问状态 ADR](../adr/2026-08-04-remove-project-access-status.md) 删除；项目系统角色、Task 可见性、成员和审批授权按 [Task 全员可见、双成员角色与全局管理员审批 ADR](../adr/2026-08-03-task-global-visibility-participants-admin-approval.md) 执行。
>
> 状态（2026-08-01）：本文涉及资源冲突、冲突中心、投入比例、冲突通知或冲突扫描的设计已由“删除资源冲突与投入比例”决策取代，仅保留历史背景，不代表当前实现。

本文记录统一账号重构后的实际边界。飞书 OAuth 是唯一登录方式；采购报销与项目管理共用账号，但业务角色相互独立。

## 1. 身份模型

```text
飞书 OAuth / 通讯录
        │ openId + unionId
        ▼
AccountIdentity ──► Account
                       │
                       ├── Person(status) ──► TaskMember / WorkSegment
                       ├── User ──► PurchaseOrder
                       ├── SystemRoleAssignment
                       └── UserRole
```

- `Account` 是全系统账号和授权主体，不再包含项目访问启用/禁用字段。所有已登录并成功解析到统一 `Account/Person` 的账号都可进入项目管理、全局读取未删除业务数据并创建 Task。
- `AccountIdentity` 保存默认租户的飞书 `openId/unionId` 唯一映射。解析时优先使用 `unionId`，缺失时以 `open:<openId>` 兼容。
- `Person` 保存展示资料并承载项目成员和投入关系。`Person.status=INACTIVE` 是通讯录业务状态：不阻止登录、全局读取和创建 Task；当前账号创建 Task 时仍自动成为 Owner，但停用 Person 不可作为其他 Task 的新增成员，也不可创建新 Segment，历史成员和历史 Segment 继续展示。
- `User` 继续承载采购报销资料和订单外键，通过唯一且非空的 `accountId` 关联 `Account`。
- 登录和通讯录同步在同一事务内按 `accountId → unionId → openId` 解析或创建 `Account/AccountIdentity/Person`，再协调 `User`。飞书 openId 轮换时更新原 User；身份指向多个账号时硬失败，不按姓名猜测合并。

## 2. 角色模型

### 2.1 项目角色

| 角色 | 范围 | 权限 |
|---|---|---|
| `SUPER_ADMINISTRATOR` | 全局，组织字段为空 | 报销最高权限、全部项目业务、账号与权限后台 |
| `PROJECT_ADMINISTRATOR` | 项目全局，组织字段为空 | 全部项目业务、全量项目审计、Tag 管理；不能管理账号 |
| 普通账号 | 无系统角色记录 | 全量读取未删除项目数据、创建 Task；其他写权限按 `TaskMember` |

项目活跃系统角色只允许上述两类全局角色，组织字段必须为空。`GROUP_LEADER` 与其他旧项目角色只保留已撤销历史；数据库 CHECK、账号管理 Zod 和服务端授权都禁止重新授予。两类全局角色在项目业务中权限相同，但只有 `SUPER_ADMINISTRATOR` 可进入账号与权限后台。

### 2.2 报销角色

`TEAM_ADMIN`、`TECH_GROUP_ADMIN`、`TEACHER`、`FINANCE` 的审批范围和采购状态机保持不变。角色现在关联 `accountId`，并记录授予、撤销操作人和时间。授权、审批收件人和签名均读取账号当前身份，旧 `UserRole.openId` 只作历史快照。

旧 `UserRole.SUPER_ADMIN` 只保留为已撤销历史，不再参与授权。运行时需要报销超管语义时，由统一 `SUPER_ADMINISTRATOR` 合成兼容角色；项目管理员不会因此获得报销权限。

### 2.3 旧项目角色

`GROUP_LEADER`、`SYSTEM_ADMINISTRATOR`、`TEAM_ADMINISTRATOR`、`RESOURCE_MANAGER`、`AUDITOR` 仅保留已撤销历史。授权上下文只读取活跃全局角色；数据库禁止再创建任何活跃旧项目角色。

## 3. Task 授权组合

Task 有效成员只允许 `OWNER/PARTICIPANT`。同一 Person 在同一 Task 中只能有一个有效角色；支持多个 OWNER，但至少一名。历史 `LEAD/MEMBER/REVIEWER/VIEWER` 保留为已结束行，不参与授权。Work Segment 的 `REVIEWER` 工作职责是独立内容字段。

- 所有已登录并成功解析到统一 `Account/Person` 的账号都可读取全部未删除 Task、计划、验收、Task 审计和完整 Segment，并可创建任意合法组织范围的 Task；创建者自动成为 OWNER。
- 非成员不能修改既有 Task 或关联 Segment。
- PARTICIPANT 可修改 Task 元数据、Tag、Draft 计划，提交 Milestone 证据和 Revision，并管理自己的 Task 关联 Segment。
- OWNER 另可管理成员、激活/结束 Task、管理任意未生效 Revision 和该 Task 全部 Segment。
- 两类全局管理员可执行所有项目写操作，并且是 Milestone/Revision 的唯一决定人；允许自审，但 Revision 仍须先提交再显式批准。
- 查询使用 `taskReadableWhere` 和 `segmentReadableWhere` 统一过滤 `deletedAt=null`；详情和显式 ID 仍执行存在性校验，不暴露逻辑删除数据。
- Task 生命周期、输入校验、乐观锁、并发检查、终态只读、关联一致性和审计始终有效。

## 4. 服务端授权与变更接口

`lib/account-authorization.ts` 提供统一上下文：

```ts
type AccountAuthorizationContext = {
  accountId: string;
  isSuperAdministrator: boolean;
  projectRoles: AccountProjectRoleRecord[];
  reimbursementRoles: AccountReimbursementRoleRecord[];
};
```

`lib/account-management.ts` 提供 `grantAccountRole()`、`revokeAccountRole()`、`assignReimbursementRole()` 和 `revokeReimbursementRole()`。Server Action 只完成 Session 认证、Zod 校验和调用领域服务；不再存在项目启用/禁用接口。

领域服务在事务中重新读取操作者的活跃超级管理员角色，不信任客户端或 Session 缓存。账号粒度 advisory lock 串行化同一目标的变更；超级管理员变更另使用全局 advisory lock。实现保证：

- 禁止撤销自己的超级管理员身份；
- 至少保留一名活跃超级管理员；
- 并发撤销不能绕过最后一名保护；
- 重复授予和撤销幂等；
- 角色、审计、站内通知和 outbox 同事务提交。

## 5. 账号与权限后台

- `/admin/accounts` 仅允许全局超级管理员访问；`/admin/roles` 服务端重定向到新地址。
- 账号列表显示头像、姓名、项目角色、报销角色和最后登录时间，并支持姓名/飞书 ID、角色、车组和技术组筛选。
- 列表采用 30 条服务端分页。桌面端为表格和详情面板；移动端为卡片和全屏详情，无横向滚动。
- 详情展示飞书身份、全局项目角色、报销角色、已撤销项目角色历史和账号安全审计。
- 普通成员是“无项目系统角色”的计算状态，不提供 `MEMBER` 授权。
- 超级管理员授予/撤销需要确认；后台不提供项目启用/禁用操作。
- 后台概览统计统一账号、超级管理员、项目管理员和报销角色；不再提供项目访问状态或活跃项目组长统计，也不提供相应操作入口。

## 6. 安全审计与通知

每次人工角色变更在同一事务中完成：

1. 写入或撤销角色；
2. 追加 append-only `DomainAuditEvent`，包含操作者、目标、前后值和范围；
3. 创建 `ACCOUNT_SECURITY` 站内通知；
4. 写入 `mandatory=true`、`channel=project-management` 的 outbox。

账号安全通知只发送给被操作人，使用通知机器人，稳定事件键以 `account-security:` 开头。payload 包含操作者、变更类型、角色/范围和时间。禁发开关、allowlist 和逐收件人投递门禁保持有效。

迁移审计使用 `source=MIGRATION`，不创建站内通知或飞书 outbox，避免上线时批量触达真实用户。移除项目访问状态时，历史 `DISABLED` 账号会写恢复审计，随后删除状态列和枚举；这只保留迁移证据，不再形成运行时授权条件。

## 7. 数据迁移与发布

发布已有数据的环境时必须按以下顺序执行：

```bash
npm run accounts:preflight  # 旧 schema 上只读检查
npm run db:deploy           # 应用统一账号 migrations
npm run accounts:validate   # 新 schema 上只读核对
```

预检报告身份多账号冲突、待创建账号数、孤儿角色、重复/非法作用域角色、双范围 `TEAM_ADMINISTRATOR` 和旧超级管理员数。任一阻断项都会非零退出。双范围旧组长不会自动拆分，管理员必须显式选择车组、技术组或两个独立分配。

统一账号历史迁移按 `unionId` 优先、`openId` 兜底关联；无法匹配的 `User` 创建统一账号、身份和 Person。该历史阶段的角色映射为：

| 旧角色 | 新结果 |
|---|---|
| 报销 `SUPER_ADMIN` | `SUPER_ADMINISTRATOR`，旧记录撤销 |
| 项目 `SYSTEM_ADMINISTRATOR` | `PROJECT_ADMINISTRATOR`；已有全局超管时不重复授予 |
| 项目 `TEAM_ADMINISTRATOR` | 当时映射为车组或技术组 `GROUP_LEADER`，后续 Task 权限迁移统一撤销 |
| `RESOURCE_MANAGER` / `AUDITOR` | 撤销，不创建新角色 |

迁移不删除旧角色行，并为每条映射或退役角色写稳定 ID 的 `source=MIGRATION` 审计；重复执行 backfill 不重复写审计，SQL notice 输出新增、当前映射、撤销、冲突和跳过统计。完成后数据库强制 `User.accountId NOT NULL`，`accounts:validate` 核对 User—Account 关联、活跃新旧角色数和 migration 审计统计。空库可直接部署，再在首位用户登录或通讯录同步后执行：

```bash
npm run db:seed -- --super-admin-open-id=<飞书 openId>
```

旧角色行继续保留为撤销历史。账号级项目访问状态已由后续独立 migration 写入历史恢复审计后物理删除；该 migration 不创建通知或 outbox。

Task 全员可见发布在统一账号迁移之后追加以下步骤：

```bash
npm run pm:task-access-preflight
npm run db:deploy
npm run pm:repair-task-approval-notifications # 默认 dry-run
```

Task migration 归一化成员为 OWNER/PARTICIPANT、回填 Task 关联 Segment 的 Participant、撤销全部非全局项目角色并保存旧审批策略审计。它不创建通知。随后在禁发维护窗口以 `npm run pm:repair-task-approval-notifications -- --apply` 重跑修复脚本，冻结旧 Reviewer/组长审批 outbox，并为仍待处理的对象补建全局管理员通知。

## 8. 测试边界

- `tests/account-management.spec.ts` 覆盖统一超管、项目管理员、旧项目角色拒绝、非超管拒绝、幂等授予/撤销、审计/outbox、自撤销保护，以及已删除项目状态输入的明确拒绝。
- `tests/functional-panels.spec.ts` 在 Desktop 与 Pixel 5 覆盖账号筛选、详情、项目管理员授予/撤销，并验证不再出现项目启用/禁用控件。
- 项目生命周期、Segment、查询安全和 UI 测试验证全员读取、OWNER/PARTICIPANT/非成员矩阵、管理员唯一审批、自审、Segment 成员一致性和状态机。
- `tests/task-access-migration.spec.ts`、`tests/project-access-status-removal-migration.spec.ts` 与 `tests/task-approval-notification-repair.spec.ts` 覆盖数据归一化、状态字段删除、零通知 migration、旧 outbox 冻结、管理员补发和幂等。
- 所有 Playwright 测试使用随机隔离 PostgreSQL target/shadow，固定 `NOTIFICATION_DELIVERY_DISABLED=true`，不联系真实飞书。

发布前执行 `npm run check`、`npm run test:e2e`、`npm run build`，并在隔离 PostgreSQL 验证 `npm run db:deploy`。
