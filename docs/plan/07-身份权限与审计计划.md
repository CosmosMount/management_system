# 统一身份、权限与审计实现

本文记录统一账号重构后的实际边界。飞书 OAuth 是唯一登录方式；采购报销与项目管理共用账号，但业务角色相互独立。

## 1. 身份模型

```text
飞书 OAuth / 通讯录
        │ openId + unionId
        ▼
AccountIdentity ──► Account ──► projectAccessStatus
                       │
                       ├── Person ──► TaskMember / WorkSegment
                       ├── User ──► PurchaseOrder
                       ├── SystemRoleAssignment
                       └── UserRole
```

- `Account` 是全系统账号和授权主体。`projectAccessStatus=ACTIVE|DISABLED` 只控制项目管理访问。
- `AccountIdentity` 保存默认租户的飞书 `openId/unionId` 唯一映射。解析时优先使用 `unionId`，缺失时以 `open:<openId>` 兼容。
- `Person` 保存展示资料并承载项目成员、投入和冲突关系。
- `User` 继续承载采购报销资料和订单外键，通过唯一且非空的 `accountId` 关联 `Account`。
- 登录和通讯录同步在同一事务内按 `accountId → unionId → openId` 解析或创建 `Account/AccountIdentity/Person`，再协调 `User`。飞书 openId 轮换时更新原 User；身份指向多个账号时硬失败，不按姓名猜测合并。
- 项目禁用不阻止飞书登录，不影响采购报销，也不阻止全局超级管理员进入账号后台。进入 `/progress` 时服务端重定向到项目禁用说明页；项目 Server Action 在事务内仍会拒绝。

## 2. 角色模型

### 2.1 项目角色

| 角色 | 范围 | 权限 |
|---|---|---|
| `SUPER_ADMINISTRATOR` | 全局，组织字段为空 | 报销最高权限、全部项目业务、账号与权限后台 |
| `PROJECT_ADMINISTRATOR` | 项目全局，组织字段为空 | 全部项目业务、全量项目审计、Tag 管理；不能管理账号 |
| `GROUP_LEADER` | 恰好一个有效车组或技术组 | 对匹配组织的 Task 拥有完整权限 |
| 普通成员 | 无系统角色记录 | 只按 `TaskMember` 授权 |

同一账号可拥有多个 `GROUP_LEADER` 分配。活跃记录统一以 `revokedAt IS NULL` 判断；数据库 CHECK 约束和部分唯一索引阻止非法范围及重复活跃授权。

### 2.2 报销角色

`TEAM_ADMIN`、`TECH_GROUP_ADMIN`、`TEACHER`、`FINANCE` 的审批范围和采购状态机保持不变。角色现在关联 `accountId`，并记录授予、撤销操作人和时间。授权、审批收件人和签名均读取账号当前身份，旧 `UserRole.openId` 只作历史快照。

旧 `UserRole.SUPER_ADMIN` 只保留为已撤销历史，不再参与授权。运行时需要报销超管语义时，由统一 `SUPER_ADMINISTRATOR` 合成兼容角色；项目管理员和组长不会因此获得报销权限。

### 2.3 旧项目角色

`SYSTEM_ADMINISTRATOR`、`TEAM_ADMINISTRATOR`、`RESOURCE_MANAGER`、`AUDITOR` 仅保留已撤销历史。授权上下文只读取活跃记录；数据库禁止再创建活跃旧项目角色。

## 3. Task 授权组合

系统角色权限与 `OWNER/LEAD/MEMBER/REVIEWER/VIEWER` 成员权限取并集，Task 生命周期、输入校验、乐观锁、并发检查和默认禁止自审始终有效。

- 超级管理员和项目管理员可管理所有 Task、Segment、Conflict、Tag 和项目审计。
- 车组组长匹配 `Task.team`；技术组组长匹配 `Task.techGroup`。Task 同时具有两个字段时按 OR 匹配。
- 两个组织字段都为空时，只有全局项目角色或 Task 成员可访问。
- 组长创建 Task 时，新 Task 至少有一个组织字段命中其范围。
- 组长修改 Task 归属时，修改前和修改后都必须命中至少一个范围；完全跨组转移只允许全局项目角色。
- 跨 Task 冲突要求组长可完整管理全部关联 Task。
- 组长在范围外若是 Task 成员，仍可按成员角色操作。
- 查询使用 `taskReadableWhere`、`segmentReadableWhere` 和 Conflict 可见性条件在数据库过滤，详情与写入事务不会先读取全量对象再做内存过滤。
- `milestone.review` 和 `revision.review` 对所有管理员继续执行自审检查；只有 Task 的 `allowSelfReview=true` 才可自审。

## 4. 服务端授权与变更接口

`lib/account-authorization.ts` 提供统一上下文：

```ts
type AccountAuthorizationContext = {
  accountId: string;
  isSuperAdministrator: boolean;
  projectAccessStatus: "ACTIVE" | "DISABLED";
  projectRoles: AccountProjectRoleRecord[];
  reimbursementRoles: AccountReimbursementRoleRecord[];
};
```

`lib/account-management.ts` 提供 `grantAccountRole()`、`revokeAccountRole()`、`setProjectAccessStatus()`、`assignReimbursementRole()` 和 `revokeReimbursementRole()`。Server Action 只完成 Session 认证、Zod 校验和调用领域服务。

领域服务在事务中重新读取操作者的活跃超级管理员角色，不信任客户端或 Session 缓存。账号粒度 advisory lock 串行化同一目标的变更；超级管理员变更另使用全局 advisory lock。实现保证：

- 禁止撤销自己的超级管理员身份；
- 至少保留一名活跃超级管理员；
- 并发撤销不能绕过最后一名保护；
- 重复授予、撤销和状态提交幂等；
- 角色、审计、站内通知和 outbox 同事务提交。

项目业务 Actor 在创建时和每次写事务内检查 `projectAccessStatus`，禁用优先于项目角色和 Task 成员权限。

## 5. 账号与权限后台

- `/admin/accounts` 仅允许全局超级管理员访问；`/admin/roles` 服务端重定向到新地址。
- 账号列表显示头像、姓名、项目访问、项目角色、报销角色和最后登录时间，并支持姓名/飞书 ID、项目状态、角色、车组和技术组筛选。
- 列表采用 30 条服务端分页。桌面端为表格和详情面板；移动端为卡片和全屏详情，无横向滚动。
- 详情展示飞书身份、多个项目组长范围、报销角色、角色历史和账号安全审计。
- 普通成员是“无项目系统角色”的计算状态，不提供 `MEMBER` 授权。
- 超级管理员授予/撤销和项目启停都需要确认。禁用提示明确说明登录与报销不受影响。
- 后台概览统计统一账号、项目启用/禁用、超级管理员、项目管理员、组长和报销角色。

## 6. 安全审计与通知

每次人工角色或项目访问变更在同一事务中完成：

1. 写入或撤销角色，或修改 `projectAccessStatus`；
2. 追加 append-only `DomainAuditEvent`，包含操作者、目标、前后值和范围；
3. 创建 `ACCOUNT_SECURITY` 站内通知；
4. 写入 `mandatory=true`、`channel=project-management` 的 outbox。

账号安全通知只发送给被操作人，使用通知机器人，稳定事件键以 `account-security:` 开头。payload 包含操作者、变更类型、角色/范围或状态和时间。项目已禁用的账号仍保留 outbox 飞书候选；站内记录在重新启用后可查看。禁发开关、allowlist 和逐收件人投递门禁保持有效。

迁移审计使用 `source=MIGRATION`，不创建站内通知或飞书 outbox，避免上线时批量触达真实用户。

## 7. 数据迁移与发布

发布已有数据的环境时必须按以下顺序执行：

```bash
npm run accounts:preflight  # 旧 schema 上只读检查
npm run db:deploy           # 应用统一账号 migrations
npm run accounts:validate   # 新 schema 上只读核对
```

预检报告身份多账号冲突、待创建账号数、孤儿角色、重复/非法作用域角色、双范围 `TEAM_ADMINISTRATOR` 和旧超级管理员数。任一阻断项都会非零退出。双范围旧组长不会自动拆分，管理员必须显式选择车组、技术组或两个独立分配。

迁移按 `unionId` 优先、`openId` 兜底关联；无法匹配的 `User` 创建统一账号、身份和 Person。角色映射为：

| 旧角色 | 新结果 |
|---|---|
| 报销 `SUPER_ADMIN` | `SUPER_ADMINISTRATOR`，旧记录撤销 |
| 项目 `SYSTEM_ADMINISTRATOR` | `PROJECT_ADMINISTRATOR`；已有全局超管时不重复授予 |
| 项目 `TEAM_ADMINISTRATOR` | 对应车组或技术组 `GROUP_LEADER` |
| `RESOURCE_MANAGER` / `AUDITOR` | 撤销，不创建新角色 |

迁移不删除旧角色行，并为每条映射或退役角色写稳定 ID 的 `source=MIGRATION` 审计；重复执行 backfill 不重复写审计，SQL notice 输出新增、当前映射、撤销、冲突和跳过统计。完成后数据库强制 `User.accountId NOT NULL`，`accounts:validate` 核对 User—Account 关联、活跃新旧角色数、项目启停账号数和 migration 审计统计。空库可直接部署，再在首位用户登录或通讯录同步后执行：

```bash
npm run db:seed -- --super-admin-open-id=<飞书 openId>
```

旧角色和旧字段的物理清理由后续独立变更处理，本次不删除历史。

## 8. 测试边界

- `tests/account-management.spec.ts` 覆盖统一超管、非法范围、非超管拒绝、幂等授予、项目禁用、审计/outbox 和自撤销保护。
- `tests/functional-panels.spec.ts` 在 Desktop 与 Pixel 5 覆盖账号筛选、详情、组长授予/撤销、项目启停、禁用说明页及采购仍可访问。
- 原项目生命周期、Segment、Conflict、查询安全和 UI 测试继续验证成员矩阵、范围过滤、自审和状态机。
- 所有 Playwright 测试使用随机隔离 PostgreSQL target/shadow，固定 `NOTIFICATION_DELIVERY_DISABLED=true`，不联系真实飞书。

发布前执行 `npm run check`、`npm run test:e2e`、`npm run build`，并在隔离 PostgreSQL 验证 `npm run db:deploy`。
