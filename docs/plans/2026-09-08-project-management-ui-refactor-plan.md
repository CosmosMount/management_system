# 项目管理 UI 全面重构计划

- 制定日期：2026-09-08。
- 状态：阶段 1 已提交并通过其验证门禁（见 §13）；阶段 2–5 的桌面实现与阶段 6 的本地验证、独立审查已完成（见 §14）。阶段 0 独立原型交付仍不补记为已完成，桌面结构决策以 §14.3 的代理试用及用户后续授权为准。未部署，不宣称完成真人验收或手机专项改版。
- 授权过程：最初只检查并保存方案；用户后续授权实现各阶段、开分支管理 Git，并允许代理扮演用户试用后大胆重构。最新范围调整为优先桌面网页，不开展手机专项改版。
- 重构范围：项目管理的导航、工作台、项目和任务列表与详情、创建与修订、审批、投入与排期、通知；本轮主验收为桌面，原 Pixel 5 测试仅作兼容性回归。
- 基本策略：重构信息架构、页面层级、操作流程和视觉规范，保留业务规则、服务端授权、审计、通知 outbox 和画布核心能力；按页面和业务闭环分阶段替换，不一次性推倒重写。

## 1. 背景与结论

当前界面的核心问题不仅是视觉样式，而是主要按照“系统有哪些功能”组织，没有按照“用户现在需要判断什么、下一步需要做什么”组织。

只调整颜色、间距和卡片圆角无法解决以下问题：

1. 重要信息不够靠前，用户进入页面后不容易判断下一步。
2. 常用操作被基础信息、画布和长内容挤到下方。
3. 页面入口、业务术语和功能边界不够清楚。
4. 多个项目、任务之间难以快速比较。
5. 移动端基本可访问，但仍有过多纵向堆叠和阅读负担。

因此，本计划以“让管理者清楚判断、让执行者直接行动”为目标，而不是给现有长页面换一套样式。

### 2.3 问题清单

| 优先级 | 问题 | 实际表现 | 使用影响 |
| --- | --- | --- | --- |
| 高 | 信息优先级不明确 | 我的工作先展示指标和大块画布，行动待办和参与任务靠后；移动端指标卡连续占据首屏 | 用户不能立即识别需要处理的事项 |
| 高 | 导航与概念混杂 | 我的工作、看板、Project、Task、资源计划、待办审批并列；看板实际为单人只读时间线 | 用户需要先学习内部功能分类 |
| 高 | 详情页堆叠功能 | 项目和任务详情将概览、画布、风险、节点、评论、动态放在长页面中，部分区域三列并排 | 阅读和操作需要反复定位 |
| 高 | 关键动作下沉 | 任务基础信息、画布和节点导航在前，节点说明、验收和审批操作更靠下 | 不容易回答“下一步做什么” |
| 高 | 长内容缺少阅读策略 | 极端样例中的项目名称和描述连续占据多屏；任务名称在标题和概览重复出现 | 没有横向溢出也可能无法高效阅读 |
| 中 | 列表不利于比较 | 卡片和大块列表逐条展示，负责人、节点、时间、异常缺少稳定对齐关系 | 管理者需要逐条阅读多个对象 |
| 中 | 画布承担过多职责 | 计划、节点定位、人员投入、创建投入、历史查看围绕画布展开 | 简单业务也需要先学习画布操作 |
| 高 | 移动端以缩窄和堆叠为主 | 指标、筛选、字段纵向排列；窄屏画布标签和节点难辨认 | 可打开不等于可高效使用 |
| 中 | 业务语言不一致 | Task、Project、Start、Terminal、Current Plan、Revision 等混用 | 状态和操作名称增加学习成本 |
| 中 | 高频工作与低频设置混排 | 通知阅读与通知偏好处于同一内容流 | 日常处理与设置缺少分层 |

长名称和长描述部分来自刻意构造的极端测试数据，不代表日常内容分布；但其确实暴露了布局缺少内容长度控制的问题。

## 3. 重构目标与范围边界

### 3.1 两类使用目标

“执行者”和“管理者”表示工作场景，不是新增权限角色；同一个人可以同时承担两种工作。

执行者进入系统后，应能直接回答：

1. 哪些事情需要我处理？
2. 当前任务处于哪个节点，需要完成什么？
3. 计划时间是什么，是否有待审或阻塞事项？
4. 我现在能提交什么，为什么某些动作不可用？
5. 如何记录本次投入？

管理者进入系统后，应能直接回答：

1. 哪些项目或任务需要关注？
2. 问题在哪里，涉及谁？
3. 哪些事项等待当前账号审批？
4. 人员在什么时间有什么安排？
5. 如何进入对象并执行已有权限允许的动作？

### 3.2 本次不做的事情

- 不新增 Project Stage，不恢复已退役的投入确认、旧审批角色等模型或流程。
- 不更改状态机、审批互斥、权限继承、事务、审计或通知机器人边界。
- 不将项目负责人身份转换为下属任务写权限。
- 不引入缺少业务口径的项目健康分、人员负载率或投入完成百分比。
- 不为 UI 重构默认增加依赖、数据库状态、迁移或新的环境开关。
- 不同时重写画布引擎和全部页面，不长期维护两套业务逻辑。
- 不将当前临时浏览器审查结果当作用户研究或全量测试结果。

## 4. 建议信息架构与术语

### 4.1 主导航

```text
项目管理
├─ 工作台
│  ├─ 我的工作
│  └─ 管理概览
├─ 项目
├─ 任务
├─ 团队排期
│  ├─ 资源计划
│  └─ 人员时间线（只读）
└─ 待办与审批

独立通知入口
├─ 通知列表
└─ 通知设置
```

上述结构为待原型确认的产品方案，不表示已经存在新路由或新 API。

约束：

- 导航归并不等于查询逻辑、编辑模式或权限归并。
- 保留 `/progress/resources` 和 `/progress/kanban` 的现有语义；后者仍为单人只读视图，不顺便改成多人选择或编辑模式。
- 现有路由、飞书和站内通知链接保持有效。
- 管理概览只整理原本可读数据，不扩大读取范围或赋予审批权。
- 普通账号是否默认显示管理概览、两种工作台视图如何切换，在阶段 0 确认；不得因此无意改变读取权限。

### 4.2 中文术语

以“项目、任务、里程碑、计划修订、开始节点、结束节点、当前计划、投入记录”等业务语言为展示方向，在阶段 0 固化术语表。技术名称可在必要的帮助或历史信息中辅助展示，但不要求普通用户依赖内部英文概念完成操作。

中文展示调整不意味着修改数据库枚举、历史审计值、通知事件键或业务对象身份。

## 5. 页面与交互设计

### 5.1 工作台

“我的工作”按以下顺序组织：

1. 需要我处理的事项。
2. 当前参与任务和当前节点。
3. 相关计划时间、待审批和阻塞提示。
4. 我的日程与投入。
5. 最近通知。

指标压缩为辅助信息，画布保留但不强制成为第一操作界面。空状态提供符合当前权限的下一步入口；停用账号保持只读。

“管理概览”以可进入明细的清单为主：

- 有未解决风险的项目和任务。
- 根据既有规则判定的到期事项。
- 等待当前账号审批的事项。
- 项目进展摘要和人员安排入口。

每项统计在阶段 0 明确数据源、全量范围、时间口径、分母、筛选条件、空值表现、查询成本和明细入口。不从当前分页结果推导全量数量，不把全员可读事项标为当前账号可处理待办。

### 5.2 项目与任务列表

桌面端优先使用字段对齐清楚的列表或表格；移动端使用同一信息结构的紧凑卡片。

| 项目列表优先信息 | 任务列表优先信息 |
| --- | --- |
| 名称、状态 | 名称、状态 |
| 负责人 | 负责人 |
| 任务进展摘要 | 当前节点、计划时间 |
| 未解决风险摘要 | 待审或阻塞提示 |
| 进入项目 | 进入任务 |

交互要求：

- 常用筛选提供快捷视图，保留原有默认筛选语义。
- 始终清楚显示当前范围和重置入口。
- 保留所有状态、分页、搜索上限提示、刷新恢复和浏览器前进后退。
- 长标题显示有限行数，同时可查看、复制完整内容。
- 终态记录始终可达，不因默认视图精简而消失。

### 5.3 项目详情

```text
项目名称 · 状态                         当前允许的操作
负责人 / 进展摘要 / 风险提示

概览 | 任务 | 计划 | 风险 | 讨论与动态 | 成员

默认概览：
项目目标摘要
需要关注的事项
任务进展摘要
关键计划信息
```

- 去掉重复大标题及不必要的嵌套卡片。
- 描述默认摘要，完整内容按需展开。
- 不再将风险、任务、动态长期放入互相挤压的三列。
- 评论有明确入口，不能被动态列表替代。
- 项目直接风险和所属任务风险保留来源区分。
- 待立项审批、驳回重提、进行中、已结束分别显示对应信息和动作。
- 项目完成率和项目是否允许结束分别表达；不以一个进度条替代两套规则。
- 项目详情内人员投入继续只读。

### 5.4 任务详情

```text
任务名称 · 状态 · 负责人                 当前主要操作
所属项目 / 计划时间

当前执行节点：……
需要完成：……
待审事项：……
阻塞原因：……

执行 | 计划 | 投入 | 讨论与动态
```

- 当前节点、交付要求和授权动作前置。
- 当前执行节点与待审批对象不一定相同，必须分别说明。
- 完整画布、历史版本、修订前后对比进入对应区域，仍可从深链直接定位。
- 元数据使用明确编辑入口，结束和删除与日常动作分开，并说明后果。
- 只读或禁用操作说明原因，不只依赖悬浮提示。
- 审批候选计划损坏时禁止不安全的批准，但保留符合权限和状态的驳回、取消等处理方式。
- 不能仅依赖 workspace 的 `can*` 字段启用按钮，还需结合状态、审批门禁和服务端结果。

### 5.5 创建、修订与审批

统一设计语言，不混用业务提交流程：

| 流程 | 建议交互 | 必须保留的语义 |
| --- | --- | --- |
| 新建任务 | 基础信息 → 计划节点 → 检查并保存 | 保存任务草稿，激活为独立动作 |
| 新建项目 | 项目信息 → 成员与关联任务 → 检查并提交 | 提交立项，不新增服务器草稿步骤 |
| 计划修订 | 修改内容 → 前后差异 → 检查并送审 | 提交即进入修订审批，不套用任务草稿流程 |

按钮区分“保存任务草稿”“提交立项”“提交修订审批”。分步呈现不新增必填业务字段，不强制任务必须包含里程碑；零里程碑计划保持合法。

审批决定前清楚展示提交人、提交时间、业务对象、请求内容、原因、证据、修改差异、当前门禁及批准后的影响。

共同要求：字段错误明确并定位首个错误；保留未保存提示、本地草稿隔离、重复提交保护；冲突时保留输入并提供恢复路径；同一任务只能存在一项待审批的约束在所有入口一致。

### 5.6 团队排期与投入

- 保留画布引擎，优先重构外围筛选、工具栏和对象操作。
- 明确区分资源计划与单人只读时间线。
- 收起低频筛选，同时显示当前筛选摘要。
- 提供明确的查看按钮、单击或键盘入口，不要求用户猜测双击行为。
- 统一图例、选中、只读、未保存和加载失败状态。
- 桌面保留拖拽，同时提供表单；移动端优先日程列表、节点详情、精确时间表单，可切换画布。
- 表单与画布使用同一合法写入口、时间精度和并发控制，不能成为权限旁路。
- 保留查询 scope、人员完整投入范围、分页或加载身份、数据预算和错误反馈；不能用项目任务勾选结果错误收窄人员的全部投入。

### 5.7 待办、通知和深链

- 待办区分当前节点工作与有权限的审批，不混入已退役的投入确认。
- 通知阅读与通知设置分层，未读数量和标记已读能力仍然可达。
- 从待办、通知或飞书进入时，自动打开对应标签、节点和必要的计划对比，滚动或高亮目标。
- 保留现有路由与 `focus`、`center`、`scale`、`#establishment` 等定位契约，以及现有查询规范化规则。
- 目标不存在或不可访问时给出明确反馈，不默默落到不相关区域。
- 标签切换、路由切换和浏览器返回必须考虑未保存输入。

## 6. 视觉、内容与可用性规范

- 每页有明确主要任务，减少多个同等强调按钮竞争注意力。
- 统一标题层级、字体、间距、边框、状态标签、表单、表格、空态与错误态；优先复用现有 UI primitives。
- 状态同时使用文字和颜色，不能只用颜色表达。
- 长标题、名称和描述有有限行数与展开策略，完整信息仍可访问；关键错误和阻塞原因不能简单截断。
- 加载、空、成功、禁用、失败、重试、冲突状态均需设计。
- 保留语义化控件、关联标签、键盘操作、可见焦点和明确按钮名称。
- 不产生意外的页面级横向滚动；画布的局部横向导航明确可见。
- 移动端不机械堆叠桌面布局；减少首屏无行动价值的信息，确保触控、表单和错误定位可用。
- 每阶段从第一版开始同时适配桌面和移动端，不把移动端作为末尾补丁。
- 按需加载必须实际减少查询和渲染，不用 CSS 隐藏冒充性能优化；懒加载同时处理缓存、深链和输入保护。

可用性验证以“找到目标信息、完成核心动作的步骤和耗时”比较新旧版本，而不是只评价截图。当前尚无真人测试基线，阶段 0 应确定代表性任务及测量方式，不能虚构改善百分比。

## 7. 分阶段实施

推荐顺序：阶段 0 → 阶段 1 → 阶段 2 → 阶段 3A → 阶段 3B → 阶段 4 → 阶段 5 → 阶段 6。每期独立交付、验证和评审；高风险门禁不能拖到最终阶段才执行。

### 阶段 0：固定需求、业务口径与原型

目标：确认新界面解决什么问题，再开始应用代码修改。

交付：

- 页面、角色、状态、动作和深链矩阵。
- 中文术语表、导航和关键页面信息层级。
- 工作台、项目详情、任务详情、创建和审批的桌面与移动原型。
- 管理概览指标定义及来源、全量范围、时间口径和成本。
- 文档差异、已有测试失败和未覆盖路径清单。
- 原型覆盖只读、待审批、驳回、长内容、零里程碑和异常候选计划。

退出条件：关键流程在原型上走通，信息优先级得到确认，产品待定项得到记录和决策，没有被实现者自行发明的业务规则。

### 阶段 1：导航、中文与视觉基础

目标：入口易理解，页面遵循一致的设计语言。

交付：导航分组、中文文案、标题与面包屑、操作分级、通用视觉规范、通知与设置分层、移动导航与长内容处理。

范围控制：先修改项目域配置；共享 `ManagementShell` 也服务采购，若触及共享布局或抽屉，必须同步回归采购，不能只测试项目域。

退出条件：所有入口双端可达、旧链接有效，长内容不挤掉导航和主要动作，键盘和触控操作正常。

### 阶段 2：工作台与列表

目标：解决进入系统不知道先看什么，以及多个对象难以比较的问题。

交付：行动优先的我的工作、口径明确的管理概览、项目和任务对齐列表、快捷筛选与范围提示、移动紧凑卡片、分页和异常反馈。

退出条件：执行者可直接识别下一项工作，管理者可从列表定位需要关注的对象；摘要与服务端全量口径一致，搜索和所有终态记录仍可达。

### 阶段 3A：项目详情

目标：默认回答项目当前情况，减少长页面和三列阅读负担。

交付：精简概览，任务、计划、风险、讨论与动态、成员分区；长内容展开策略；立项待审、驳回重提、进行中和终态布局；项目与任务风险来源区分。

退出条件：可清晰理解项目进展和关注事项；深链自动打开对应内容；评论、审批历史及只读投入完整保留。

### 阶段 3B：任务详情

目标：默认回答当前节点、下一步动作、待审和阻塞状态。

交付：执行主线前置，计划、投入、证据、修订对比和历史信息分区；管理动作与日常动作分离；只读、审批互斥和异常候选处理。

退出条件：从待办和通知进入后直接定位目标节点或审批对象；授权动作准确，不能因重排内容隐藏错误或阻塞原因。

审批深链必须随阶段 3 同步交付，不等阶段 4 再补。

### 阶段 4：创建、修订与审批闭环

目标：降低复杂表单理解成本，减少误操作。

分成三个独立验证的闭环：

1. 任务草稿创建、编辑、恢复与激活。
2. 修订创建、修改、差异展示与送审。
3. 项目立项、节点验收和任务结束审批。

退出条件：双端完整闭环，字段错误、未保存内容、账号与对象隔离、版本冲突、重复提交、跨类型审批互斥和候选异常均有覆盖；核对 UI、数据库状态、审计和适用的 outbox，而非仅验证按钮可点击。

### 阶段 5：排期外围与复杂移动交互

目标：保留专业能力，同时支持不使用拖拽的用户。

交付：资源计划和只读人员时间线的导航整合，筛选及选中对象详情，移动列表与表单、桌面画布的等价能力，密集数据和跨时间窗口处理，URL 状态与未保存保护。

退出条件：不用拖拽也能完成合法操作；只读边界、人员完整投入范围、时间精度、数据预算、并发控制和前进后退行为没有退化。

基础移动适配从阶段 1 开始，本阶段只处理更复杂的排期交互。

### 阶段 6：全链路验收与分批替换

目标：证明界面更清晰，同时没有破坏业务。

交付：完整回归、代表性可用性比较、文档更新、剩余问题记录、按页面或业务闭环替换及回退说明。

退出条件：适用检查与回归通过，独立评审没有新的可执行问题，已知高严重性问题清零；不长期保留两套业务逻辑。不能由最终阶段承担前几期遗漏的权限、审批或移动基础可用性问题。

## 8. 业务与技术保护边界

### 8.1 对象、权限与状态

- Project 是立项对象和任务容器，当前没有 Project Stage；任务可不属于项目，最多属于一个项目。
- 全员可读不等于全员可操作；停用人员保留读取，但不能业务写入。
- 项目负责人不继承下属任务写权限，采购组长身份不提供项目审批权。
- Task 草稿、激活、Revision 送审是不同动作；激活仍需合法计划、开始时间已到和至少一名在职负责人。
- 允许零里程碑任务，不能在新建引导中增加强制里程碑要求。
- 同一任务的里程碑验收、修订和结束审批保持互斥。
- 修订批准前，候选计划不能混入当前正式计划；历史证据和审批轮次保留。
- 项目完成率分子仅计成功完成任务，分母排除取消任务；项目结束由草稿和进行中任务阻塞，空项目仍可结束。两者不能混用。
- 删除项目解除任务归属，不删除任务；已完成项目禁止删除的规则保持不变。
- 投入不新增类型、确认状态或完成百分比；创建、改绑和历史终态关联记录分别沿用已有服务端规则。

### 8.2 数据、通知与实现

- 复用服务端领域入口、权限帮助函数、验证和查询，不在客户端复制规则或直接访问数据库。
- 保留事务、锁版本、投入更新时间冲突校验、幂等、审计和通知 outbox。
- 普通通知继续使用通知机器人，审批机器人只用于提交或请求审批；不新增未跟踪的直发路径。
- 保留画布引擎之外的查询 scope、分页身份、加载预算、错误反馈与选择安全规则。
- 本计划不要求数据库迁移；未来若发现必要的模型变化，应单独明确需求和授权，不作为布局调整夹带实现。

### 8.3 文档差异

制定日期的审查发现：`docs/TECH.md` 部分旧段落仍提到投入确认及六条待办流，而当前实现的待办类型不含投入确认；部分路由说明也未完整列出现有入口。

阶段 0 登记差异，以当前实现及相符的现行说明为基线；实施相关阶段更新对应文档，不能默默选择旧说明并恢复退役流程。本次保存计划不修改这些既有文档，也不宣称差异已经解决。

### 14.3 桌面试用后的结构性修正（实施前决策）

两位独立代理分别扮演管理者和执行者，通过受控 Playwright 浏览器操作并查看截图。管理者项目详情在 1440×1000 下，通用标题位于约 101px、重复项目标题约 259px、时间线约 629px，而只有一条任务的任务列表仍在约 1325px；讨论在约 2342px。执行者同样观察到重复标题、被长成员名称撑高的资料卡和约 450px 宽的中间填写区。通过操作不等于体验达标。

本轮验收标准与实施顺序：

1. 工作台：统计压成摘要，待处理事项先于资料；完整个人日程独立视图，保留日程定位深链。列表只保留一组搜索、范围、状态及优先级控件，删除等价快捷过滤的重复层。
2. 项目详情：只有一个主标题；默认显示任务概览及风险提示，而非完整时间画布；计划与投入、风险讨论等独立切换。成员和长描述按需展开，立项审批上下文与权限不丢失。
3. 任务详情：默认进入当前节点执行，填写区获得主要宽度；计划与投入、风险讨论、活动记录分开。保留计划选择、历史对比和待审批门禁，不把危险管理操作作为默认主按钮。
4. 表单与排期：区分基本资料、计划节点与检查保存；低频字段渐进披露，报错能定位字段。排期保留既有画布与精确时间编辑，压缩默认说明，不改时间精度或查询预算。
5. 状态与可访问性：视图写入 URL，刷新、前后退和现有深链可用；切换分区保留已填写内容，隐藏画布不能以零宽度覆盖原视口；键盘和无 JavaScript 的链接导航保留。
6. 验证：添加桌面首屏、长文案、空状态、权限及视图状态回归，独立审查后再提交。每个阶段的执行结果另行记录，未完成的全量测试不得记为通过。

此决策取代 §14.2 的重复快捷筛选与单纯调整 DOM 顺序方案；不改变数据库、审批、审计、通知和服务端授权。
